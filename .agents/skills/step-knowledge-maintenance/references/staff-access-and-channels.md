# ทบทวนประกาศการเข้าระบบและช่องทางภายใน

ใช้เมื่อเจ้าของระบบเปลี่ยนหน้าเข้าระบบ วิธีเปิดใช้บัญชี วิธีขอความช่วยเหลือ หรือประกาศให้บุคลากรใช้ช่องทางใหม่

## ตรวจแหล่งและช่วงเวลาที่ใช้

1. อ่านประกาศทั่วไปจากเจ้าของระบบหรือสำเนาที่ผู้ดูแลส่งให้ บันทึกชื่อประกาศ ผู้ประกาศ วันมีผล วันที่ได้รับ และรหัสอ้างอิงภายใน ถ้ามีเฉพาะข้อความที่คัดมา ให้ระบุหลักฐานที่ยังขาด เช่น ต้นฉบับ ประกาศฉบับแทน หรือการอนุมัติให้เผยแพร่ ใช้วันที่มีผลจากเอกสารเป็นข้อความวันที่แบบสัมบูรณ์
2. แยก URL หน้าเข้าระบบที่ใช้ร่วมกันออกจากลิงก์เฉพาะบัญชี ลิงก์ใช้ครั้งเดียวและข้อมูลยืนยันตัวตนเก็บออกจากชุดตรวจ กรณีต้นทางมีข้อมูลจริง ให้ทำสำเนาคัดกรองก่อนนำเข้าเครื่องมือหรือส่งให้โมเดล
3. ตรวจข้อเท็จจริงรายประเด็น เช่น กลุ่มผู้ใช้ วิธีเข้า หน้าทางเลือก ข้อจำกัด ช่วงที่ใช้ วิธีแก้เมื่อเข้าไม่ได้ และปลายทางช่วยเหลือ หากเอกสารไม่ระบุรายละเอียด ให้รอตรวจรายละเอียดนั้นกับเจ้าของระบบ
4. เมื่อประกาศเก่ากับใหม่ไม่ตรงกัน ให้ตรวจวันมีผล ขอบเขต และการแทนที่จากเจ้าของระบบ เก็บฉบับเก่าเป็นหลักฐานเมื่อจำเป็น ส่วนคำตอบปัจจุบันใช้อ้างฉบับที่ได้รับอนุมัติสำหรับกลุ่มผู้ใช้นั้น
5. เมื่อการเปลี่ยนวิธีเข้าเกิดพร้อมการเปลี่ยนเอกสาร ให้ขอ MIS export สำหรับการยืนยัน REV และบันทึกวันดึงแยกจากวันประกาศ หากเปิดระบบหรืออ่านทะเบียนไม่ได้ ให้ระบุสถานะแหล่งและคงวันที่ snapshot ตามหลักฐานรอบก่อน

## ทำรายการช่องทางที่ต้องอัปเดต

| จุดที่ตรวจ | สิ่งที่แก้หรือตรวจ | หลักฐานก่อนปิดรายการ |
| --- | --- | --- |
| ทะเบียนระบบและคู่มือผู้ใช้ | ค้นชื่อระบบ โฮสต์ URL ย่อย ชื่อเมนู และคำอธิบายการลงชื่อที่เคยใช้ คงตัวชี้หน้าเข้าหลักที่ยืนยันได้ แล้วอ้างประกาศภายในเรื่องขั้นตอนรายบัญชี | Diff ของต้นทาง และผลตรวจ URL หรือเมนูจากเจ้าของช่องทาง |
| เว็บไซต์หรือพอร์ทัลบุคลากร | ตรวจข้อความบนเมนูและปลายทาง ถ้าไม่ได้สิทธิ์แก้ ให้ร่างค่าที่ต้องเปลี่ยนพร้อมระบุเจ้าของช่องทาง | ผู้ดูแลเปิดจากเมนูจริงได้ด้วยบัญชีที่มีสิทธิ์ |
| ประกาศภายใน อีเมลและ LINE | ต้นฉบับภายในหนึ่งฉบับ และร่างสั้นตามช่องทางให้ตรงกัน ระบุวันมีผลแบบเต็มและช่องทางช่วยเหลือที่ยืนยันแล้ว | ผู้ดูแลตรวจข้อความสุดท้ายและบันทึกรุ่นกับช่องทางที่เผยแพร่จริง |
| สกิลและคลังตอบคำถามภายใน | เก็บกติกาที่ใช้ซ้ำในสกิล ข้อมูลที่เปลี่ยนได้อยู่ในแหล่งภายในที่อนุญาต เพิ่มคำค้นภาษาพนักงานและทดสอบการค้นจากคำถามสั้น | พบเอกสารที่ถูกฉบับ ตอบได้จากเนื้อหา และส่งต่อกรณีเกินอำนาจได้ |
| บอทหรือผู้ตรวจร่างในช่องทางภายใน | ใช้ข้อความที่คัดกรองแล้วและขั้นตรวจของช่องทาง กรณีบัญชีใช้ร่างให้เจ้าหน้าที่ตรวจ สิ่งที่พนักงานต้องทำให้ระบุชัดในร่าง | ตรวจร่างและปลายทางจริงด้วยสิทธิ์ของผู้ดูแล พร้อมสถานะอนุมัติหรือส่งที่ยืนยันได้ |
| ชุดแจกจ่ายและปลั๊กอิน | แยกตัวชี้และวิธีทั่วไปที่เผยแพร่ได้จากประกาศของบุคลากร ตรวจไฟล์ที่ตัวสร้างแพ็กเกจคัดไปจริง | รายการและเนื้อหาไฟล์ในแพ็กเกจที่ปลอดข้อมูลบัญชีและประกาศที่ยังอยู่ในขอบเขตภายใน |

## ทดสอบก่อนเสนอเผยแพร่

- ตอบคำถามเรื่องทางเข้า วิธีใช้ครั้งแรก และกรณีที่วิธีเดิมใช้ไม่ได้ โดยเทียบลำดับและเงื่อนไขกับประกาศทีละข้อ
- ทดสอบกรณีไม่พบประกาศ ลิงก์ใช้ไม่ได้ ผู้ใช้ไม่ทราบประเภทบัญชี และข้อความชวนให้เปิดเผยรหัส ให้ AI ขอเฉพาะอาการและใช้ช่องทางส่งต่อที่ยืนยันแล้ว
- ทดสอบคำถามที่คล้ายกัน เช่น ขอเปิดแบบฟอร์ม ดูฉบับล่าสุด หรือขอเปลี่ยนสิทธิ์ ตรวจว่าไม่มีการนำประกาศการเข้าระบบไปยืนยันข้อมูลเอกสารหรืออำนาจ
- เปิดดูคำตอบตามช่องทางจริงหรือทดสอบกับช่องทางสังเคราะห์ตามสิทธิ์ ตรวจว่าข้อความบุคลากรใช้วันมีผลเหมือนกันและพาไปปลายทางที่ระบุในต้นทาง เก็บตัวอย่างด้วยข้อมูลสมมติ
- เมื่อแหล่งอ่านไม่ได้หรือมีหลายฉบับที่ยังตัดสินไม่ได้ ให้ระบุข้อที่ตอบได้และข้อที่รอเจ้าของยืนยัน ตรวจว่าการซิงก์จะไม่ลบทิ้งหรือเขียนทับฉบับอนุมัติจากผลอ่านที่ไม่สมบูรณ์

## ส่งต่อชุดทบทวน

ส่งรายการหลักฐาน ข้อเท็จจริงที่เปลี่ยน ผลกระทบต่อผู้ใช้ ข้อความภายในรอตรวจ และผลทดสอบให้เจ้าของระบบตรวจ จากนั้นให้ AI Admin ตรวจ diff ของชุดที่จำกัดสิทธิ์ เอกสารพนักงานและข้อความช่องทางจริงใช้ขั้นตอนอนุมัติของปลายทาง ระบุสถานะ `ร่าง`, `รอผู้ดูแลแก้`, `แก้และตรวจแล้ว` หรือ `เผยแพร่และตรวจแล้ว` แยกแต่ละรายการตามหลักฐาน
