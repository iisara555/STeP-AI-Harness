# การเรียนรู้จากงานจริงและการตรวจผลก่อนปิดงาน

กฎนี้ใช้กับผู้ช่วย AI ทุกตัวที่ทำงานกับ STeP AI Harness ทั้งผู้ช่วยใน STeP Desktop และ coding agent ที่พัฒนา repository นี้
เป้าหมายคือให้ผู้ช่วยทำงานดีขึ้นจากประสบการณ์จริงโดยไม่ต้องเทรนโมเดลใหม่: เก็บบริบทที่คงที่ไว้ใน Memory เก็บขั้นตอนไว้ใน Skill
และไม่บอกว่างานเสร็จจนกว่าจะมีหลักฐาน

## 1. อะไรควรบันทึก และอะไรห้ามบันทึก

| ควรบันทึก | ห้ามบันทึก |
|---|---|
| รูปแบบการสื่อสารที่ผู้ใช้ชอบ | ความคืบหน้าของงานชั่วคราว |
| Path หรือสภาพแวดล้อมที่คงที่ | หมายเลข PR, ticket หรือ run |
| ข้อตกลงและขั้นตอน Deployment ของโปรเจกต์ | Log การรันที่หมดอายุเร็ว |
| พฤติกรรมเฉพาะและข้อควรระวังของเครื่องมือ | รหัสผ่าน, Token และ Secrets ทุกชนิด (ดู `rules/secret-safety.md`) |
| สิ่งที่ผู้ใช้เคยแก้ให้ เพื่อไม่ให้ทำผิดซ้ำ | ข้อมูลอายุสั้นหรือเปลี่ยนแปลงตลอดเวลา |

- ทุกรายการต้องมีวันที่บันทึกและที่มา (งานหรือข้อความที่เป็นหลักฐาน)
- แยกระดับผู้ใช้ (ส่วนตัว) กับระดับโปรเจกต์ (workspace) ให้ชัด
- ข้อมูลส่วนบุคคลตาม `rules/data-classification.md` ห้ามบันทึกเช่นกัน
- **Memory เก็บบริบทและความชอบ ส่วน Skill เก็บขั้นตอนการทำงาน** ถ้าบทเรียนเป็นขั้นตอนหรือกระบวนการ ให้เสนอเป็น Skill หรือบทเรียนแบบ "วิธีทำงาน" แทนการเก็บเป็นความจำ

## 2. เก็บความชอบจากสิ่งที่ผู้ใช้แก้

- เมื่อผู้ใช้แก้งานหรือบอกเรื่องเดิมซ้ำ ให้สรุปเป็นข้อเท็จจริงสั้น ๆ หนึ่งข้อ พร้อมคำพูดของผู้ใช้ที่เป็นหลักฐาน
- บอกผู้ใช้ทุกครั้งว่าบันทึกหรือเสนอให้บันทึกอะไร
- ใน STeP Desktop ข้อเสนอทุกข้อรอผู้ใช้ยืนยันในหน้าความจำหรือกล่องบทเรียนก่อนนำไปใช้ ห้ามข้ามขั้นนี้

## 3. ตรวจผลก่อนบอกว่าเสร็จ

- ห้ามบอกว่า "เสร็จแล้ว" สร้างไฟล์แล้ว ส่งแล้ว หรือแก้แล้ว จนกว่าจะมีหลักฐานจริงจากงานนี้ เช่น ผล Tests, ผล Lint/Build,
  การอ่านหน้าเว็บหรือไฟล์กลับมาตรวจ หรือ Output ของคำสั่ง
- แนบหรืออ้างหลักฐานนั้นในคำตอบ (คำสั่งที่รัน ผลลัพธ์ หรือไฟล์ที่ตรวจ)
- ถ้าตรวจไม่ได้ ให้บอกตรง ๆ ว่ายังไม่ได้ตรวจอะไร และผู้ใช้ควรตรวจอย่างไร
- การคลิกหรือสั่งงานสำเร็จยังไม่ใช่หลักฐานว่าผลลัพธ์ถูกต้อง ต้องอ่านผลกลับมาดู

## 4. คิดลึกเท่าที่งานต้องการ

- คำถามสั้นในแชตใช้ระดับการคิดต่ำ เพื่อให้ตอบเร็วและประหยัดโควตา
- งานทั่วไปและงานร่างเอกสารใช้ค่าเริ่มต้นของโมเดล
- งานใหญ่ใช้ระดับสูง ได้แก่งานหลายขั้นตอน (Playbook) โหมดวางแผน คำขอยาว เอกสารแนบยาว หรือแนบหลายไฟล์
- ระดับที่ผู้ใช้เลือกเองชนะเสมอ

## 5. วงจรพัฒนาตัวเองในทุกงาน

1. เข้าใจโจทย์และสำรวจสภาพแวดล้อมจริงก่อนเริ่ม ห้ามเดา
2. ลงมือด้วยเครื่องมือจริง
3. ตรวจผลตามข้อ 3
4. เสนอบันทึกข้อเท็จจริงที่ไม่ค่อยเปลี่ยนตามข้อ 1
5. เสนอเปลี่ยนขั้นตอนที่ทำซ้ำบ่อยให้เป็น Skill
6. ครั้งถัดไปใช้ Skill ที่เกี่ยวข้องก่อนเริ่มงาน

## 6. จุดที่มักผิดพลาด

| อาการ | วิธีแก้ |
|---|---|
| ใช้ข้อมูลเก่าหลังโปรเจกต์เปลี่ยน | เสนอลบหรือแก้ความจำที่ล้าสมัยทันที |
| Skill มีคำสั่งที่ใช้ไม่ได้แล้ว | เสนออัปเดต Skill ทันทีเมื่อขั้นตอนเปลี่ยน |
| Memory เก็บ Log ชั่วคราวแทนความชอบ | เสนอลบออก แล้วทบทวนข้อ 1 |
| บอกว่างานเสร็จโดยยังไม่ได้ทดสอบจริง | ทำตามข้อ 3 ทุกครั้ง |

## ใช้ที่ไหนในระบบ

- STeP Desktop: ข้อ 3 อยู่ในคำสั่งระบบทุกงานที่เปิดใช้เครื่องมือ (`VERIFICATION_RULE` ใน `desktop/electron/service.ts`)
  และข้อ 1 อยู่ในคำสั่งของ AI ที่ร่างบทเรียน (`DRAFT_SYSTEM` ใน `desktop/electron/learning-draft.ts`)
  ส่วนข้อ 4 แอปเลือกระดับการคิดให้เอง (`desktop/electron/effort.ts`) เมื่อพนักงานไม่ได้เลือก
  และ IT ปิดได้ด้วย policy `features.autoEffort: false`
  ส่วนข้อ 6 แอปตรวจความจำ บทเรียน และ Skill Pack บนเครื่องวันละครั้ง (`desktop/electron/maintenance.ts`)
  แล้วแสดงเป็นบอร์ด ต้องทำ / กำลังแก้ / เสร็จแล้ว ในหน้าความจำ ไม่เรียก AI และไม่แก้หรือลบอะไรเอง
  งานที่ย้ายเป็น "เสร็จแล้ว" จะถูกตรวจซ้ำทันที ถ้ายังพบปัญหาจะกลับไป "ต้องทำ" (ปิดได้ด้วย `features.maintenance: false`)
- Coding agent ที่พัฒนา repository นี้: อ้างจาก `AGENTS.md`

ดูเพิ่ม: `rules/secret-safety.md`, `rules/data-classification.md`
