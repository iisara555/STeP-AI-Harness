# Agenda → Run of Show Specification

เอกสารนี้เป็นมาตรฐานของ Playbook `brief-to-run-of-show` สำหรับแปลงกำหนดการหรือบรีฟงานหนึ่งงานให้เป็น Run of Show ระดับคิว พร้อมออกเป็นชีตที่ทีมใช้บนหน้างานได้

## 1. One Event = One Run

- งานหนึ่งงานต่อหนึ่ง Playbook Run
- งานหลายวันอยู่ใน Run เดียวกันได้ โดยแยกด้วยคอลัมน์ `Day` แต่ **งานคนละงานต้องแยก Run**
- ห้ามรวมกำหนดการของหลายงานเข้าเป็นตารางเดียวอัตโนมัติ แม้จะแนบมาในข้อความเดียวกัน
- งานเตรียมก่อนวันงาน (`D-1`) และงานเก็บ (`Teardown`) อยู่ใน Run เดียวกับวันงาน เพราะเอกสารจริงของ STeP ทำแบบนี้อยู่แล้วและทีมชุดเดียวกันเป็นคนอ่าน

## 2. Source Fact vs Planning Assumption

### Source Fact
ข้อมูลที่มีหลักฐานในกำหนดการ บรีฟ หนังสือเชิญ หรือ TOR เช่น:
- ช่วงเวลาของแต่ละวาระ
- ชื่อและตำแหน่งของวิทยากรที่ตอบรับแล้ว
- สถานที่ ห้อง และจำนวนผู้เข้าร่วมที่ยืนยันแล้ว
- หัวข้อบรรยายที่ตกลงแล้ว
- เวลาที่ต้องจบแน่นอน

### Planning Assumption
ข้อมูลที่ AI เสนอเพื่อให้คุมเวทีได้ เช่น:
- การแตกหนึ่งวาระออกเป็นหกคิวย่อย
- เวลา 2 นาทีสำหรับช่วงที่พิธีกรเชื่อม
- คิวเผื่อเวลาต่อ block
- `Timer` ที่เสนอให้สั้นกว่าช่วงเวลาจริงเพื่อกันผู้พูดเกิน

Planning Assumption ต้องติดป้ายชัดเจนและแก้ได้ ห้ามเขียนปนกับเวลาที่ต้นทางระบุ

### AI Recommendation
ความหมายของรหัส Scene/Format ที่เสนอ และช่วงเวลาซ้อมที่แนะนำ อยู่คนละชั้นกับ Planning Assumption เพราะต้องให้ทีม AV ยืนยันก่อนใช้

## 3. Show Parameters

สร้าง Parameter Block ก่อนแตกคิว:

| Parameter | Rule |
| --- | --- |
| Event Name | ใช้ชื่อทางการตามต้นทาง ห้ามแก้การสะกดเอง |
| Date(s) | `YYYY-MM-DD` แปลงจาก พ.ศ. แล้วเก็บของเดิมไว้ |
| Venue / Room | ตามต้นทาง ถ้ายังไม่ยืนยันให้เป็น `รอยืนยัน` |
| Expected Pax | ใช้เพื่อประเมินเวลาเข้าออกห้อง ไม่ใช่เพื่อคำนวณอะไรเอง |
| Doors Open | เวลาเปิดให้ผู้เข้าร่วมเข้าห้อง |
| Hard Stop | เวลาที่ต้องจบแน่นอน ถ้ามี |
| Show Caller / MC / AV Lead | บทบาทที่ต้องมีชื่อจริงก่อนวันซ้อม |
| Source Document | ไฟล์ต้นทางที่ใช้ทำตารางนี้ |

## 4. โมเดลเวลาสองระดับ และนาฬิกาสามเรือน

- `Block Time` คือช่วงของวาระ `Cue Time` คือช่วงของคิวย่อย และทุก `Cue Time` ต้องอยู่ในกรอบ `Block Time`
- `Block Duration` เก็บ **ตามที่ต้นทางระบุ** แม้ไม่ตรงกับผลรวมของคิว ส่วนต่างเป็นสิ่งที่ต้องรายงาน ไม่ใช่สิ่งที่ต้องแก้เงียบ ๆ
- `Timer` คือเลขที่ผู้พูดเห็น เป็นค่าอิสระจากความยาวคิว
  - `Timer` สั้นกว่าช่วงเวลา มักตั้งใจ ต้องบันทึกเหตุผล
  - `Timer` ยาวกว่าช่วงเวลา **เป็นบั๊กเสมอ** ต้องขึ้น Open Items

## 5. Lane Contract

โครงสร้างคอลัมน์และกติกาการเติม lane อยู่ที่ `skills/creative/event-run-of-show/references/lane-contract.md`

หลักที่ Playbook บังคับ:
- หนึ่งแถวคือหนึ่ง action
- ทุกแถวถือค่า `Block` ของตัวเอง ห้าม merge cell
- ทุกคิวมี `Lead` หนึ่งคนหรือหนึ่งบทบาท
- lane ที่ไม่มีข้อมูลเลยให้ลบออกจากตาราง แล้วบันทึกไว้ที่ Show Parameters ว่า `ไม่ใช้ในงานนี้`

## 6. Enum Confirmation Policy

รหัส Scene/Format ค่าที่ขึ้นจอ และตัวย่อชื่อคน **ไม่ใช่มาตรฐานกลางขององค์กร** เป็นข้อตกลงรายงานกับทีม AV ที่รับงานนั้น

- Playbook เขียนรหัสที่เสนอไว้ใน tab `Cue Enums` โดยตั้ง `รอยืนยัน` ทุกแถว
- ห้ามใช้รหัสในตารางคิวหลักจนกว่าช่อง `ยืนยันโดย` จะมีชื่อจริง
- ในโหมด Review ให้อนุมานความหมายจากไฟล์ที่ได้รับเท่านั้น และรายงานความไม่สอดคล้องภายในไฟล์นั้น ห้ามเทียบกับไฟล์งานอื่น

## 7. Privacy Policy

- ชีตที่ออกจาก Playbook นี้ **ไม่มีคอลัมน์ข้อมูลติดต่อ**
- ห้ามเขียนเบอร์โทร ทะเบียนรถ เลขบัตรประชาชน เลขเที่ยวบิน หรือเวลาเดินทางของบุคคล
- ก่อนอ่านไฟล์แนบให้ใช้ Privacy Gate ตาม [Privacy preflight](privacy-preflight.md)
- ถ้าไฟล์ต้นทางเป็นสำเนาของงานเก่า ต้องล้างชื่องาน ชื่อคน และข้อมูลติดต่อของงานเดิมออกก่อน แล้วรายงานว่าล้างอะไรไปบ้าง

## 8. สิ่งที่ Playbook นี้ไม่ทำ

- ไม่ตัดสินคอนเซ็ปต์งาน ธีม หรือผังโซน — เป็นงานของ `event-concept`
- ไม่ตัดสินลำดับเกียรติหรือลำดับการเชิญ VIP — เป็นอำนาจของเจ้าของงานและผู้มีอำนาจลงนาม
- ไม่ทำหรือแก้สไลด์และ VTR ที่คิวอ้างถึง — เป็นงานของ `presentation-design`
- ไม่ร่างขอบเขตงานจ้างทีมแสงเสียง จอ หรือออแกไนเซอร์ — เป็นงานของ `tor-government-writing`
- ไม่ยืนยันว่าคิวทำทันจริง ความเป็นไปได้พิสูจน์จากการซ้อมเท่านั้น
