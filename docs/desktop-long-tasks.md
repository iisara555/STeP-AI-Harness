# งานยาว เอกสาร และการเขียนโค้ดใน Desktop

ส่วนนี้เป็น source ที่กำลังพัฒนา ยังไม่ใช่หลักฐานว่าอยู่ในชุดติดตั้งที่เผยแพร่แล้ว
ใช้ระบบงานเดิมของ Desktop และนำแนวทางจาก Hermes มาปรับให้เหมาะกับงานพนักงาน

## สลับคำถามกับงานเอกสาร

- ในงานเอกสาร คำถามอย่าง “ช่วยอธิบายว่าวัตถุประสงค์ข้อนี้หมายถึงอะไร” เปิดคำตอบ **ถามแทรก** โดยไม่เปลี่ยนร่าง เป้าหมาย แผน หรือประวัติงานหลัก
- ใช้ปุ่ม **ถามแทรก** หรือ `/btw คำถาม` ได้ระหว่างที่งานหลักกำลังทำงาน คำตอบอ้างอิงภาพสถานะ ณ ตอนถามและระบุรุ่นเอกสาร การแก้ร่างในภายหลังไม่เปลี่ยนคำตอบเก่า
- การถามแทรกใช้เอกสารในภาพสถานะและความรู้องค์กรที่ลงทะเบียนไว้ ปิดเครื่องมือและการค้นเว็บ จึงใช้ยืนยันข้อมูลสด เช่น ปฏิทินล่าสุด ไม่ได้ หากต้องอ่านบริการภายนอก ให้เริ่มงานใหม่
- ปุ่ม **เริ่มงานใหม่** ข้างช่องพิมพ์ในงานเอกสารย้ายข้อความที่ยังไม่ได้ส่งไปงานใหม่ ร่างเดิมยังอยู่ คำขอที่กำกวมและไม่ใช่คำถามยังถือเป็นการแก้ร่าง จึงควรใช้ปุ่มนี้เมื่อเปลี่ยนเรื่อง

ภาพสถานะประกอบด้วยคำขอเดิม ร่างที่มีผลหรือข้อเสนอที่ตรงกับรุ่นปัจจุบัน (สูงสุด 60,000 ตัวอักษร) และแผนงาน
ใช้บัญชีและโมเดลเดียวกับงานหลัก ผ่านกติกาความเป็นส่วนตัวและการอนุมัติส่งข้อมูลเดิม
เก็บคำถามแทรกล่าสุดสิบรายการแยกจากข้อความที่ใช้ทำงานหลัก มีคำถามแทรกได้ครั้งละหนึ่งรายการต่อหนึ่งงาน
และยังนับรวมในขอบเขตงานพร้อมกันของแอป การหยุดงานยกเลิกทั้งงานหลักและคำถามแทรก

## แก้เอกสารเฉพาะส่วนจากแชต

ตัวอย่าง: “แก้เฉพาะข้อ 2 ให้กระชับ”, “แก้เฉพาะวัตถุประสงค์”, “แก้ย่อหน้าที่ 1 ของหัวข้อ 2”
โฮสต์หาเป้าหมายจากหัวข้อหรือย่อหน้าในเอกสารจริง แล้วขอ patch ที่ผูกกับเป้าหมาย รุ่น และ hash ของเนื้อหา
AI ส่งกลับได้เฉพาะส่วนที่เลือก โฮสต์ประกอบข้อเสนอโดยคง structured nodes นอกส่วนนั้นไว้
จึงรักษาตาราง รูป และการจัดรูปแบบนอกเป้าหมายได้โดยไม่ให้ AI เขียนเอกสารทั้งฉบับใหม่

ข้อเสนอแสดงให้ตรวจและยอมรับตามขั้นตอนเดิม การแก้ด้วยมือระหว่างรอทำให้ข้อเสนอเก่าใช้ทับรุ่นใหม่ไม่ได้
หากหาเป้าหมายไม่เจอหรือพบซ้ำ จะให้ระบุส่วนอีกครั้ง การเลือกย่อหน้านับเฉพาะย่อหน้าระดับเอกสาร
เมื่อระบุหัวข้อด้วยจะนับภายในหัวข้อนั้น ไม่เลือกข้อความในเซลล์ตาราง
เนื้อหาและการจัดรูปแบบ **ภายในส่วนที่เลือก** ยังเป็นข้อเสนอใหม่จาก Markdown และต้องตรวจทาน

## Auto compact และทำตามแผนต่อเนื่อง

ระบบ compact เก็บสรุปบทสนทนาเก่าลง SQLite พร้อมจำนวนข้อความที่ครอบคลุมและ hash ของประวัติต้นทาง
ถ้าประวัติเดิมตรงกันจะใช้สรุปซ้ำ เมื่อมีข้อความเพิ่มจะสรุปต่อจากส่วนใหม่ และเมื่อประวัติเปลี่ยนจะสร้างสรุปใหม่
บันทึกสรุปเมื่อ compact สำเร็จเท่านั้น เก็บ transcript ฉบับเต็มไว้ และไม่ย่อคำขอปัจจุบัน กติกาหลัก หรือสถานะงาน
สถานะที่ส่งซ้ำประกอบด้วยเป้าหมาย แผนที่อนุมัติ รายการค้าง และรุ่นเอกสาร

หลังอนุมัติแผนจาก **วางแผนก่อนลงมือ** เลือก **ทำตามแผนแบบต่อเนื่อง** เพื่อทำต่อโดยไม่ต้องพิมพ์ “ต่อ” ทุกรอบ
โฮสต์อ่านความคืบหน้าที่บันทึกจริงจาก `plan_update` ระหว่างรอบ และหยุดเมื่อเสร็จ ติดขัด รอคำตอบ เกิดข้อผิดพลาด
ถูกยกเลิก หรือสถานะรายการงานไม่เดินหน้า ขอบเขตต่อครั้งคือสามรอบ สิบนาที และหยุดรับ provider/tool turn เพิ่ม
เมื่อใช้ถึง 50,000 โทเคนที่ผู้ให้บริการรายงาน คำขอที่เริ่มไปแล้วอาจใช้เกินยอดนี้ จึงไม่ใช่วงเงินค่าใช้จ่ายตายตัว
การอนุมัติไฟล์ คำสั่ง และผลข้างเคียงยังใช้กติกาเดิม

เมื่อเปิดแอปใหม่จะเก็บแผนและสรุปไว้ แต่งานที่กำลังทำจะเป็น interrupted และคำถามแทรกที่ค้างจะเป็น error
ไม่ส่งคำขอหรือทำผลข้างเคียงเดิมซ้ำอัตโนมัติ ผู้ใช้เลือกทำต่อเองได้
การทำเครื่องหมายเสร็จยังอาศัยผลของ agent และหลักฐานเครื่องมือ ไม่มีตัวตัดสินอิสระรับรองว่าเป้าหมายธุรกิจสำเร็จ

## เขียนและตรวจโค้ด

เลือก workflow **เขียนและตรวจโค้ด** เพื่อให้ agent อ่านคำแนะนำโครงการ แก้ผ่าน `patch` ตรวจ diagnostics
ใช้คำสั่ง test/typecheck/build ที่โครงการกำหนด แก้ข้อผิดพลาด และตรวจ diff พร้อมผล exit code ก่อนสรุป
ในโหมด Ask การแก้ไฟล์ยังอยู่ใน Changes รอให้ตรวจและกดยอมรับ การตรวจไฟล์ก่อนยอมรับจึงยังเห็นโค้ดเดิม

เครื่องมือ `code_diagnostics` ใช้ TypeScript language service จริงสำหรับ JavaScript/TypeScript และ JSX/TSX
ใน worker แยกที่ไม่รันโค้ด ปลั๊กอิน หรือ config script ของโครงการ อ่าน snapshot ที่ผ่านขอบเขต workspace เดิม
สูงสุดยี่สิบไฟล์ ไฟล์ละ 200 KB รวม 1 MB พร้อม relative imports ที่หาได้ จำกัดเวลา worker สิบห้าวินาที
ตรวจ hash และ workspace ซ้ำก่อนคืนผล ปฏิเสธ binary/UTF-8 ไม่ถูกต้อง ใช้ compiler และ standard libraries ที่บันเดิลในแอป

ผลมี `incomplete` และ `truncated` แยกกัน การตรวจนี้ไม่โหลด tsconfig หรือ dependency ภายนอก
จึงไม่แทน project build/test หรือ LSP สำหรับภาษาอื่น คำสั่งของโครงการยังต้องรันและอ่านผลจริง
การติดตั้ง dependency, commit, merge และ deploy ไม่ได้เกิดขึ้นเพียงเพราะเลือก workflow นี้

- `desktop/test/code-diagnostics.test.ts`: พบ semantic error จริง แก้แล้วหาย อ่าน relative import และปฏิเสธ path นอก workspace

ผลจำลองยืนยันพฤติกรรมของโฮสต์ ไม่ใช่คะแนนคุณภาพคำตอบจากโมเดลจริงหรือหลักฐานว่าเทียบเท่า Hermes ทุกด้าน
