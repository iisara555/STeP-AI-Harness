# Learning Inbox — บทเรียนที่ผู้ใช้ตรวจและยืนยัน

Learning Inbox เป็น self-improvement ระยะแรกของ STeP Desktop: เก็บคำแก้ไขเป็นข้อเสนอ ให้คนตรวจ แล้วเลือกบทเรียนที่ยืนยันแล้วเป็นบริบทในงานถัดไป ข้อมูลอยู่ใน SQLite ของแอป แยกตามพื้นที่งานและทีมบนเครื่องเดียวกัน ไม่ต้องติดตั้งบริการความจำหรือโมเดลเพิ่มเติม

## วิธีใช้

1. พิมพ์ `/learn` หรือ `/learn <บทเรียน>` ในช่องสนทนา หรือเปิด **กล่องบทเรียน** จากเมนูบทสนทนา/Command Palette
2. ตั้งชื่อ เลือก **ความชอบในการทำงาน** หรือ **วิธีทำงานเฉพาะเรื่อง** ระบุบทเรียนและเหตุผลที่เสนอ สำหรับวิธีทำงาน ให้ใส่คำที่ใช้จับคู่กับคำขอ เช่น `receipt,ใบเสร็จ`
3. กด **บันทึกข้อเสนอ** ข้อเสนอที่รอตรวจยังไม่ถูกใช้ในงาน
4. ตรวจเนื้อหาและที่มา แก้ไข ปฏิเสธ หรือ **ยืนยันใช้บทเรียน** การยืนยันอนุญาตให้ส่งบทเรียนเป็นบริบทให้ผู้ให้บริการ AI ในงานที่เกี่ยวข้องตามนโยบายการส่งข้อมูลปัจจุบัน
5. ใน **บทเรียนและประวัติรุ่น** สามารถเสนอแก้ไข หยุดใช้ หรือคืนค่ารุ่นก่อนหน้าได้ ทุกการแก้ไขต้องยืนยันใหม่ การคืนค่าจะสร้างรุ่นใหม่เพื่อรักษาประวัติ

**ให้ AI ร่างบทเรียนจากงานนี้:** เมื่อเปิดกล่องบทเรียนจากงานที่ทำเสร็จแล้ว จะมีปุ่มนี้ให้กด และใส่ "ให้ AI เน้นเรื่อง" ก็ได้ ระบบทำงานดังนี้

1. ส่ง 30 ข้อความล่าสุดและร่างงานให้ AI ที่งานนั้นเชื่อมต่ออยู่ โดยปิดบังข้อมูลอ่อนไหวก่อนส่ง AI รอบนี้ใช้เครื่องมือไม่ได้
2. AI ร่างบทเรียนได้ไม่เกิน 5 ข้อ เป็นความชอบ หรือเป็นวิธีทำงานพร้อมคำกระตุ้น แต่ละข้อมีข้อความจากงานที่เป็นหลักฐาน และเหตุผล
3. แต่ละข้อเข้ากล่องเป็น **ข้อเสนอรอตรวจ** ที่มา "AI ร่างจากงาน" ผ่านการตรวจรูปแบบและ privacy เดียวกับข้อเสนอที่พิมพ์เอง ข้อที่มีข้อมูลส่วนบุคคลถูกทิ้ง วิธีทำงานที่ไม่มีคำกระตุ้นที่ใช้ได้ก็ถูกทิ้ง
4. ข้อเสนอเหล่านี้ไม่เข้า prompt จนกว่าจะกดยืนยัน

กติกาที่ AI ต้องทำตาม (นำมาจาก reviewer ของ Hermes Agent):

- เขียนเป็นขั้นตอน ไม่เล่าเหตุการณ์
- ห้ามบันทึกวิธีที่ยังไม่สำเร็จว่าเป็นวิธีที่เชื่อถือได้
- ห้ามสรุปว่าเครื่องมือใช้ไม่ได้จากปัญหาชั่วคราว
- ห้ามใส่ข้อมูลส่วนบุคคลหรือความลับ
- ไม่มีบทเรียนที่ควรเก็บ ให้ตอบว่างดีกว่าเดา

การร่างแต่ละครั้งเสีย tokens ของบัญชีนั้น และนับในหน้าการใช้งาน ใช้ไม่ได้ในโหมด Plan

ข้อเสนอความจำที่มีอยู่จาก feedback/บทสนทนาจะแสดงในกล่องนี้ด้วย **นำมาตรวจเป็นบทเรียน** จะย้ายข้อเสนอเข้ามาโดยรักษาหลักฐานและ session ต้นทาง และยังต้องยืนยันก่อนใช้ ขั้นตอนย้ายทำใน transaction เดียว จึงไม่ทำข้อเสนอหายหากบันทึกไม่สำเร็จ

ตัวอย่าง: เสนอ “ถ้าใบเสร็จขาดข้อมูล ให้ระบุว่าไม่ทราบและขอเอกสารเพิ่ม ห้ามเดา” เป็นวิธีทำงาน โดยใช้คำกระตุ้น `receipt,ใบเสร็จ` พร้อมเหตุผลจากคำแก้ไขที่ผู้ใช้ตรวจแล้ว เมื่อยืนยัน บทเรียนจะถูกแนบกับงานใหม่ที่มีคำดังกล่าว

## ขอบเขตและการตรวจสอบ

- `/learn` เปิดแบบฟอร์ม ไม่เรียกโมเดลเอง AI ร่างเฉพาะเมื่อกดปุ่ม "ให้ AI ร่างบทเรียนจากงานนี้" ซึ่งเสีย tokens หนึ่งครั้ง การบันทึก ยืนยัน และย้อนรุ่นไม่มีค่าเรียกโมเดล แต่บทเรียนที่ใช้ในงานเพิ่ม input tokens ของงานนั้น
- ความชอบใช้กับทุกคำขอในพื้นที่งาน/ทีมเดิม วิธีทำงานจับคู่ substring แบบไม่สนตัวพิมพ์จากคำคั่นด้วยจุลภาคหรือขึ้นบรรทัดใหม่ เฉพาะคำยาวตั้งแต่สองตัวอักษร ไม่ใช่ semantic search
- เลือกตามลำดับบทเรียนที่ยืนยันครั้งแรก สูงสุด 5 บทเรียน และเนื้อหารวม 8,000 ตัวอักษรต่องาน ไม่ส่งหลักฐานที่มาเข้า prompt
- บทเรียนเป็นคำแนะนำที่ผู้ใช้ตรวจแล้ว ไม่ใช่ข้อเท็จจริงองค์กรที่ตรวจสอบแล้ว ไม่เปลี่ยน host permissions, governance, managed Skills หรือน้ำหนักโมเดล
- ตรวจรูปแบบและ privacy ก่อนบันทึก/ยืนยัน และตรวจบทเรียนซ้ำก่อนใช้ แม้ปิด privacy check สำหรับแชตทั่วไปก็ยังตรวจข้อมูลที่เก็บเป็นบทเรียน การตรวจนี้ไม่รับรองความถูกต้องของเนื้อหาหรือคุณภาพคำตอบ
- โหมด Plan อ่านได้ แต่ไม่บันทึก ย้าย ยืนยัน ปฏิเสธหรือย้อนรุ่น หน้าต่างที่เปิดค้างไว้ในบริบทเก่าจะเขียนข้ามพื้นที่งาน/ทีมไม่ได้ ให้ปิดแล้วเปิดกล่องใหม่
- การแก้ไขและย้อนรุ่นเทียบรุ่นปัจจุบันก่อนบันทึก จึงไม่ทับการเปลี่ยนแปลงที่เกิดหลังเปิดข้อเสนอ หากชนกัน ให้ปฏิเสธข้อเสนอเก่าแล้วเสนอจากรุ่นล่าสุด
- หยุดใช้มีผลกับการประกอบบริบทครั้งถัดไป ข้อความที่ส่งให้โมเดลหรืออยู่ในประวัติสนทนาแล้วเรียกคืนไม่ได้ เริ่มบทสนทนาใหม่เมื่อต้องการทดสอบโดยไม่มีบริบทเก่า
- เก็บสูงสุด 20 ข้อเสนอรอตรวจ, 100 บทเรียน, 100 รุ่นต่อบทเรียน และ 8 MB ต่อพื้นที่งาน/ทีม เมื่อครบรุ่นยังหยุดใช้ได้อีกหนึ่งครั้ง รุ่นที่มีบทเรียนยืนยันจะรักษาที่มาไว้ ข้อเสนอที่ปฏิเสธและไม่มีรุ่นอ้างอิงอาจถูกล้างเมื่อสร้างข้อเสนอใหม่
- การแยกพื้นที่งาน/ทีมเป็นการแยกบริบทภายในโปรไฟล์แอป ไม่ใช่ระบบบัญชีผู้ใช้หลายคนหรือการเผยแพร่บทเรียนให้ทั้งทีม

## เสนอบทเรียนให้ผู้ดูแล Skill (ระยะที่ 2)

บทเรียนในกล่องใช้ได้เฉพาะพื้นที่งานและทีมบนเครื่องนี้ ถ้าบทเรียนควรใช้กับทุกคนที่ใช้ Skill ขององค์กร (เช่น "ใบเสร็จไม่มีเลขผู้เสียภาษีให้เขียนว่าไม่พบ ห้ามเดา" สำหรับ Skill ตรวจใบเสร็จ) ให้ส่งเป็นข้อเสนอไปที่ผู้ดูแล Skill นั้น แอปไม่แก้ Skill ขององค์กรเอง

**ฝั่งพนักงาน**

1. ในหัวข้อ **บทเรียนและประวัติรุ่น** บทเรียนที่เปิดใช้อยู่มีหัวข้อ **เสนอให้ผู้ดูแล Skill**
2. เลือก Skill แล้วกด **สร้างไฟล์ข้อเสนอ** เลือกที่บันทึกไฟล์ `skill-proposal-<skill>-<วันที่>.md`
3. ส่งไฟล์ให้ผู้ดูแล Skill ของทีมเจ้าของ แอปแสดงชื่อทีมนี้ให้หลังบันทึก

ไฟล์ข้อเสนอมีข้อมูลดังนี้:

- Skill รุ่น ทีมเจ้าของ และทีมผู้เสนอ
- บทเรียนรุ่นที่ยืนยันแล้ว พร้อมที่มาและหลักฐาน
- patch ของ `SKILL.md` ที่เพิ่มบทเรียนใต้หัวข้อ `## บทเรียนจากการใช้งาน`
- กรณีทดสอบสำหรับ `evals/skills/<skill>.json`

ไฟล์ทั้งไฟล์ผ่านการตรวจข้อมูลส่วนบุคคลก่อนบันทึก ไฟล์ที่ไม่ผ่านจะไม่ถูกสร้าง ใช้ไม่ได้ในโหมด Plan

**ฝั่งผู้ดูแล Skill**

1. ตรวจว่าบทเรียนถูกต้องและใช้ได้กับทุกทีม ไม่ใช่กรณีเฉพาะของผู้เสนอ
2. แก้ `prompt` ของกรณีทดสอบในไฟล์ให้เป็นโจทย์จำลองที่ไม่มีข้อมูลจริง
3. ใน repository รัน `node scripts/apply-skill-proposal.mjs <ไฟล์ข้อเสนอ>` (มี `--dry-run` ให้ตรวจก่อน) สคริปต์จะ:
   - ตรวจว่า patch แก้เฉพาะ `SKILL.md` ของ Skill นั้น และยัง apply ได้ ถ้า Skill เปลี่ยนไปหลังสร้างข้อเสนอ สคริปต์จะไม่ apply
   - ไม่ยอมรับกรณีทดสอบที่ยังเป็น TODO
   - apply patch และเพิ่มกรณีทดสอบ (dimension `regression`) เข้า `evals/skills/<skill>.json` ถ้า Skill ยังไม่มีไฟล์ eval ครบ 4 มิติ จะเก็บไว้ที่ `evals/skills/pending/<skill>.lessons.json` แทน
   - รัน `scripts/validate-repo.js`
   - ไม่ commit หรือ push เอง
4. ย้ายบทเรียนไปไว้ในหัวข้อที่เหมาะกว่าได้ แล้วเปิด Pull Request ตามปกติ CI จะ route โจทย์ในกรณีทดสอบจริง จึงต้องเป็นโจทย์ที่เลือก Skill นี้
5. เทียบผลของ Skill เดิมกับฉบับใหม่ก่อน merge (ระยะที่ 3)

## ทดสอบ Skill เดิมเทียบฉบับใหม่ก่อน merge (ระยะที่ 3)

การที่ AI เขียนบทเรียนเพิ่ม ไม่ได้พิสูจน์ว่าคำตอบครั้งต่อไปจะดีขึ้น ก่อน merge การแก้ Skill จึงต้องรันโจทย์ชุดเดียวกันกับ Skill ทั้งสองรุ่น:

```sh
STEP_EVAL_BASE_URL=https://api.example.com/v1 STEP_EVAL_MODEL=<model> STEP_EVAL_KEY=<key> \
  node scripts/skill-eval-compare.mjs meeting-summary --base origin/main [--cases id,id] [--runs 3] [--out report.md] [--record]
```

- **รุ่นเดิมและรุ่นใหม่:** รุ่นเดิมคือ `SKILL.md` ที่ `--base` (ค่าเริ่มต้น `HEAD`) รุ่นใหม่คือไฟล์ใน working tree
- **โจทย์:** ทุกกรณีใน `evals/skills/<skill>.json` และ `evals/skills/pending/<skill>.lessons.json` ที่มี `outputAssertions` ข้ามกรณีที่ prompt ยังเป็น TODO ซึ่งรวมโจทย์ที่ไม่ได้ใช้สร้างบทเรียน จึงเห็นว่าการแก้ทำให้ส่วนอื่นแย่ลงไหม
- **วิธีให้คะแนน:**
  - โมเดลตอบโจทย์ด้วย Skill แต่ละรุ่น
  - ผู้ตรวจ (`STEP_EVAL_JUDGE_MODEL` ถ้าไม่ตั้งใช้โมเดลเดียวกัน ซึ่งเชื่อถือได้น้อยกว่า) ตัดสิน assertion ทีละข้อ
  - คำตัดสินที่อ่านไม่ได้นับเป็นไม่ผ่าน
- **ผล:** ตารางคะแนนรายกรณี รุ่นเดิม → รุ่นใหม่ และ assertion ที่รุ่นใหม่ยังพลาด ถ้ามีกรณีใดแย่ลง exit code เป็น 1
- `--record` บันทึกผลลง `baseline.modelSideRun` ตามมาตรฐานการเขียน Skill
- `--dry-run` บอกจำนวนโจทย์และจำนวนครั้งที่เรียกโมเดล โดยไม่เรียกจริง
- key อ่านจาก environment เท่านั้น ไม่รับทาง command line
- **บน GitHub:** workflow **Skill eval (old vs new)** (`.github/workflows/skill-eval.yml`) รันแบบสั่งเอง เลือก Skill กับ base ได้ และแนบรายงานเป็น artifact ต้องตั้ง secrets `STEP_EVAL_BASE_URL`, `STEP_EVAL_MODEL` และ `STEP_EVAL_KEY` ก่อน การรันใช้ tokens ของบัญชีนั้น
- **ข้อจำกัด:** ผลจากโมเดลไม่คงที่ ใช้ `--runs` หลายรอบเพื่อดูความแปรปรวน ถ้าคะแนนต่างกันเล็กน้อย ยังไม่ใช่หลักฐานว่าดีขึ้น

## สิ่งที่ยังไม่อยู่ในระยะนี้

ยังไม่มี background reviewer (การร่างด้วย AI ทำเมื่อพนักงานกดเท่านั้น), dashboard วัดคุณภาพ, curator/การรวมบทเรียนซ้ำ, การแชร์บทเรียนทีม, การเลื่อนเป็น Skill อัตโนมัติ (ระยะที่ 2 ทำได้เพียงเสนอให้ผู้ดูแลตรวจ) หรือระบบลบประวัติรายบทเรียน UI ย้อนรุ่นแสดงเนื้อหาเดิม ส่วนหลักฐานและ candidate IDs ของรุ่นที่ยืนยันเก็บใน SQLite

ขั้นต่อไปควรเพิ่ม evaluation และงบประมาณการ review ก่อนเปิดการสร้างข้อเสนออัตโนมัติ ต้องวัดอัตราความผิดซ้ำและเวลาที่คนแก้งาน ไม่ใช้จำนวนบทเรียนเป็นหลักฐานว่า AI เก่งขึ้น

## Verification

```sh
cd desktop
npm test
npm run build
node test/learning-smoke.mjs
```

`test/learning-draft.test.ts` ตรวจการอ่านคำตอบของ AI แบบเข้มงวด และขอบเขตของข้อมูลที่ส่งให้ AI ส่วน smoke ตรวจว่า AI ร่างแล้วได้ข้อเสนอรอตรวจ ข้อที่มีอีเมลไม่เข้ากล่อง และบริบทเก่าหรือโหมด Plan ร่างไม่ได้ Unit tests ตรวจสถานะก่อน/หลังยืนยัน การแยกบริบท conflict, privacy, transaction, prompt bounds และการคงข้อมูลหลัง restart ส่วน Electron smoke ใช้หน้าจอจริง, IPC, SQLite และ provider adapter กับโมเดลจำลอง ตรวจว่า pending ไม่เข้า prompt, ยืนยันแล้วเข้า, หยุดใช้แล้วไม่เข้า และย้อนรุ่นได้หลัง restart ผลนี้ยืนยัน workflow ไม่ได้พิสูจน์ว่าคำตอบจากโมเดลจริงดีขึ้น
