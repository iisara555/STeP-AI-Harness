# ตรวจงานร่างเอกสารและส่งออก — 8 ตุลาคม 2569

ตรวจเส้นทางของทั้งห้าเครื่องมือ ตั้งแต่ฟอร์ม → Skill และ working template → คำตอบ AI → ข้อเสนอ → ร่างที่แก้ไขได้ → DOCX/PDF ใช้แบบบันทึกที่เจ้าของงานส่งมาเทียบโครง ฟอนต์ และส่วนลงนามในเครื่องเท่านั้น ไม่เก็บต้นฉบับ ชื่อบุคคล รายชื่อผู้ร่วมงาน หรือข้อมูลโครงการจริงใน repository

## ปัญหาที่แก้

เดิมคำตอบ AI ทั้งก้อนถูกบันทึกเป็นข้อเสนอและนำเข้า editor ดังนั้นคำอธิบาย ตารางตรวจ Skill และรายการยืนยันจึงกลายเป็นหน้าของไฟล์ส่งออกด้วย ส่วน `<br/>` ถูกอ่านเป็นข้อความ และบรรทัดชื่อ/ตำแหน่งที่ไม่ถูกจำแนกเป็นส่วนลงนามได้รับรูปแบบย่อหน้าเนื้อหา

- `document_draft` เก็บเฉพาะตัวเอกสาร; `document_review` เก็บผลตรวจ แหล่งที่ขาด และขั้นตอนถัดไป Host แยกสองส่วนก่อนเก็บข้อเสนอ และแสดงผลตรวจแยกในแอป
- ผลตรวจยังอยู่หลังใช้ร่าง โดยผูกกับ revision ที่ AI ตรวจ เมื่อร่างเปลี่ยน แอปแจ้งให้ตรวจใหม่ ผลตรวจไม่ใช่การอนุมัติหรือหลักฐานว่าตรวจหน้าของไฟล์แล้ว
- ข้อเสนอเก่าที่มีหัวข้อผลตรวจที่รู้จักถูกแยกเมื่อกดใช้ร่าง ไม่ตัดตารางกิจกรรม/งบ/งานติดตามที่เป็นเนื้อหาเอกสาร รูปแบบ envelope ที่ขาด ซ้ำ หรือซ้อนกันถูกปฏิเสธ
- `<br>`, `<br/>` ใน Markdown ปกติกลายเป็น native hard break ไม่ประมวลผล HTML ทั่วไป และไม่เปลี่ยนข้อความโค้ดที่ตั้งใจแสดง literal
- บันทึกสั้นใช้ย่อหน้าต่อเนื่อง ไม่บังคับหัวข้อเลข ๑–๔ ใช้ชื่อช่องส่วนงาน/ส่วนราชการตามแบบ มีช่องผู้เสนอความเห็นและผู้พิจารณาเมื่อเจ้าของเรื่องระบุ โดยไม่เติมคำสั่ง อนุมัติ หรือลายมือชื่อ
- DOCX ใช้ justification ที่ไม่กระจายบรรทัดสุดท้ายเต็มหน้ากระดาษ จำแนกชื่อและตำแหน่งในส่วนลงนามแยกจากเนื้อหา บันทึกใช้ TH Sarabun New 16 pt และหัวบันทึก 30 pt bold; profile อื่นยังใช้ TH Sarabun PSK และเลือกฟอนต์ได้
- เลขหนังสือกับวันที่อยู่คนละคอลัมน์ใน PDF เช่นเดียวกับ tab ของ DOCX โดยไม่เปลี่ยนเลขอ้างอิงหรือเติมปีให้วันที่กำกวม
- ไฟล์แนบเลือกเป็นต้นเรื่องของงานนี้หรือแบบฟอร์ม/ตัวอย่างได้ ส่งจุดประสงค์นั้นไปกับคำขอและ Skill checks แบบตัวอย่างใช้เฉพาะโครง/ชื่อช่อง ไม่ถือค่าที่กรอกไว้เป็นข้อเท็จจริงของงานใหม่ การเลือกชนิดไฟล์ไม่ยืนยันค่าเครื่องอ่านหรือให้อำนาจอนุมัติ ทั้งนี้ผลทดสอบ provider จำลองไม่ได้พิสูจน์ว่าโมเดลจริงจะทำตามเสมอ

## ส่งออกเมื่อยังไม่มีโฟลเดอร์

ปุ่มส่งออกเปิด native folder picker ที่เลือกหรือสร้างโฟลเดอร์ได้ แล้วส่งออกต่อและจำโฟลเดอร์นั้น ผู้ใช้ไม่ต้องเปิด Settings ก่อน หากโฟลเดอร์เดิมถูกลบให้เลือกใหม่ การยกเลิกไม่เปลี่ยนโฟลเดอร์หรือร่าง ไม่เปิด dialog ซ้ำสำหรับการส่งออกเอกสารเดียวกัน และบันทึก workspace โดยผสาน settings ปัจจุบันหลังเลือกโฟลเดอร์ เก็บ action gate ของการส่งออกไว้

แบบที่ส่งมาใช้เทียบโครงและรูปแบบบันทึก ไม่ได้ถูกนำไปแจกจ่ายเป็น master template เส้นทางแบบร่างทั่วไปในช่วงตรวจแรกยังไม่รักษาวัตถุ ตาราง เส้น และตำแหน่งทุกจุดจาก DOCX ที่แนบแบบ pixel-for-pixel (เส้นทางแม่แบบ native DOCX เพิ่มในส่วนท้าย) การรับรองแบบหน่วยงาน รุ่นปัจจุบัน อำนาจลงนาม และข้อกฎหมายยังเป็นการตัดสินใจของเจ้าของเอกสาร

เอกสารที่ใช้ร่างไปแล้วก่อนแก้ครั้งนี้ไม่ถูกเปลี่ยนหรือตัดหน้าอัตโนมัติ ให้สั่งแก้ไข/ร่างใหม่เมื่อจำเป็น แล้วตรวจร่างก่อนใช้ ข้อเสนอที่ยังไม่ได้ใช้จะได้รับการแยกหัวข้อผลตรวจที่รู้จักเมื่อกดใช้ร่าง

เพื่อยืนยันความตรงกับงานของทุกทีม ควรมีแบบมาตรฐานของ TOR หนังสือ โครงการ และรายงานประชุม รวมถึงแบบบันทึกแต่ละวัตถุประสงค์ พร้อมระบุรุ่น/เจ้าของแบบ ช่องบังคับ ชื่อช่องและลำดับลงนาม ตัวอย่างกรอกที่ถูกต้องและตัวอย่างที่ต้องปฏิเสธ ใช้สำเนาตัดข้อมูลจริงเมื่อต้องเพิ่มเป็น fixtures ใน public repo

ทดสอบใน cloud/Linux ไม่ใช่การรับรอง layout ของ Word ทุกเวอร์ชันบน Windows/macOS หรือความถูกต้องตามกฎหมาย รวมใน Desktop 0.5.29 ไม่เปลี่ยน Harness version หรือ default policy และไม่ส่งเอกสารจริงไปยัง AI provider ในการตรวจนี้


## แม่แบบ DOCX ภายใน — Desktop 0.5.29

เชื่อมเส้นทางแม่แบบในเครื่องสำหรับบันทึก หนังสือ โครงการ และรายงานประชุมฝ่าย ใช้ต้นฉบับ MIS สำหรับ QA นอก repo ส่วน TOR คงแบบ 16 หัวข้อเดิมตามที่เจ้าของงานอนุมัติ ไฟล์ภายในและข้อมูลเข้าสู่ระบบไม่รวมใน commit, release หรือ installer

Host เก็บ bytes ที่เลือกเป็น snapshot ส่วนตัวของ session ไม่รับ path/key จาก renderer เพื่อแทนแม่แบบ จำกัดการอ่านผ่าน file descriptor แม้ไฟล์โตระหว่างอ่าน ส่งเฉพาะชื่อหัวข้อที่รู้จักและความหมายคอลัมน์ให้ AI แทนข้อความตัวอย่าง แยกสิทธิ์ใช้โครงแม่แบบจากสิทธิ์ส่งข้อความต้นเรื่อง หาก Privacy Gate ไม่คืนข้อความ จะใช้เป็นต้นเรื่องไม่ได้ ร่างที่ส่งออกใช้ editor ล่าสุดและคงรูปแบบย่อหน้า/run, tab, ภาพ/ตรา, grid ตาราง/เซลล์รวม, header/footer และ section ของไฟล์ต้นฉบับ ตัดภาพลายเซ็นเก่าในเนื้อหาและ bytes ภาพที่ไม่ถูกใช้ออกจากเอกสารใหม่ แม่แบบต้องเป็นแบบเปล่า ภาพ/ข้อความคงที่ใน header/footer ยังเป็นส่วนของแม่แบบที่เจ้าของต้องตรวจ

ตรวจจำนวนและความหมายคอลัมน์ที่ระบบรู้จัก ปฏิเสธการสลับจำนวนกับราคา ไม่ตัดเนื้อหาหรือลดตารางเงียบ ๆ แม่แบบที่มี macro, embedded object, external resource, active field, tracked/control content หรือ ZIP/XML เกินขอบเขตจะไม่ใช้เป็นแม่แบบ Native-template PDF ให้เปิด DOCX ตรวจใน Word และบันทึก PDF; PDF ของแบบร่างทั่วไปยังใช้ได้

เพิ่ม document-template.test.ts, document-template-store.test.ts, template-snapshot.test.ts และ document-template-smoke.mjs (4 ประเภท) ในคำสั่งทดสอบ โดย fixtures ใน repo เป็นข้อมูลสังเคราะห์ทั้งหมด QA ต้นฉบับ MIS ใช้ข้อความร่างสังเคราะห์และเก็บนอก repo ตรวจผ่าน UI/IPC จริงครบ 4 แบบ และแปลงด้วย LibreOffice ตรวจทุกหน้า: บันทึก 1 หน้า หนังสือ 1 หน้า โครงการ 1 หน้า รายงานประชุม 2 หน้า แต่ TH SarabunIT๙ ของบันทึก/หนังสือยังไม่ติดตั้งใน cloud จึงเป็น fallback และไม่รับรองการแบ่งหน้า/ฟอนต์ของ Word แบบเป๊ะ ต้องตรวจบนเครื่องพนักงานที่มีฟอนต์ตรงก่อนใช้ ไม่อ้างความแม่นยำของ AI กับเอกสารจริง

เก็บหลักฐานคลัง MIS, แหล่งที่มา, checksum, ข้อขัดแย้งของรุ่นและงานต่อยอดไว้นอก repo ตามคำขอเจ้าของ งานทะเบียนแหล่ง/ความสดใหม่, การเชื่อม WI/QP และ golden eval ทำต่อหลัง Release แม่แบบ ไม่เปลี่ยนกฎการเบิกหรือ default policy จากข้อมูลที่ยังไม่ทวน

การตรวจรวมสำหรับ Desktop 0.5.29: `npm test` 949 ข้อ ผ่าน 947 ข้าม 2; `npm run desktop:test` 506 ข้อ ผ่าน 504 ข้าม 2 ตามเงื่อนไขเดิม ผ่าน validators, formatting, TypeScript/build และ package whitelist มี regression ผ่าน UI/IPC สำหรับการส่งซ้ำ/ลบงานระหว่างรอ hook และการคงขอบเขต Privacy Gate ของไฟล์ต้นเรื่อง ชุด Electron smoke และ installer checks บน Windows/macOS อยู่ใน release workflow ก่อนเผยแพร่
