# Receipt document packets and FM-AF-014

Employees can prepare local expense cases from **ผู้ช่วยเบิกจ่าย → ชุดเอกสารเบิกจ่าย**. The case records whether payment has already occurred (reimbursement or advance clearing) or is still awaiting Finance. It does not submit to MIS, approve an expense, determine eligibility or execute a payment.

## Receipt voucher layout

The editable FM-AF-014 draft follows the owner-supplied STeP examples: A4, TH Sarabun New, centered receipt-voucher title, right-aligned agency/date block, recipient/address/received-from fields, a three-column ruled item table, amount in figures and Thai words, and separate blank recipient/payer signature areas. Native Word cells and paragraphs remain editable. Word embeds all four pinned font faces. PDF printing embeds the regular/bold faces locally.

The form identifier/revision/effective date match the active FM-AF-014 V02 entry in `docs/knowledge/mis-master-lists.md`. The printed retention wording follows the supplied V02 examples. This reconstruction is a draft layout, not a newly issued controlled form; the controlled version in MIS remains authoritative. No completed source PDF, personal identity, address or signature is bundled. The sample outputs and native smoke use synthetic values only.

`receipt_voucher` means FM-AF-014. `disbursement_voucher` means a Finance payment voucher. The old `payment_voucher` reading is accepted only as an alias for `receipt_voucher`; old records must never acquire the new disbursement meaning. A disbursement voucher alone is not treated as a receipt in the existing pre-check.

## Local case and source review

- Adding PDF/PNG/JPG files copies their selected bytes into app-owned storage. The original is never changed. Copies are SHA-256-bound; export refuses altered copies and refuses destinations that overwrite selected originals or managed sources.
- A packet supports 40 files, 250 source pages, 25 MB per file and 100 MB total. Password-protected or unreadable PDFs are rejected. Imports are bounded, and a failed batch does not commit a partial source list.
- Employees can reorder files, include/exclude pages, classify mixed PDFs per page and explicitly confirm the selected pages after comparing them with the source. Changing a page's type clears its comparison state. No automatic whole-folder OCR runs.
- Checked receipt reuse is an explicit action bound to the host's current immutable receipt bytes. Only recipient/date/description/amount values and their source link are retained; full OCR text and unrelated fields are not copied into the packet. Existing manual voucher fields are preserved. Prefill never confirms the new voucher.
- Editing voucher content clears its confirmation. Decimal calculations operate in satang and reject malformed values. A document packet never adds invoice, receipt and transfer-slip totals together, because they may describe the same expense.
- Case edits save locally with revision conflict detection. Errors remain visible; the latest saved packet can be reloaded. Removing an attachment removes its managed copy, not the original.

## UI layout and states

The packet view extends ReceiptApp's existing Operate surface, IBM Plex Sans Thai typography and shared STeP yellow/dark theme tokens. The outer `ชุดเอกสารเบิกจ่าย` mode keeps receipt review and packet preparation together. It has three parts: the case list (`เรื่องเบิกจ่าย`, each case with its category and evidence count), the chat inside the open case, and the case panel. The parts follow the page's own width through a container query: below 1,180 px the case list becomes a row above the chat, and below 760 px everything stacks. In the case panel, three freely navigable steps show case details, ordered evidence, and drafts/exports in turn. Employees can return to earlier steps without losing their work; the current step is announced and keyboard focus moves to its heading. Evidence recommendations show a compact status first, with activity and finance choices, reasons and source references available on demand. Page selection and classification expand within each source. The final step switches between `ใบสำคัญรับเงิน` (FM-AF-014) and `ใบสำคัญจ่ายสำหรับ AFP` and contains the combined export.

The AFP draft separates each item's gross amount, withholding tax and other deductions. Blank deductions remain unknown and leave the net amount pending; zero must be explicit. The checked-data import button starts from reviewed FM-AF-014 values while preserving manual edits. The QP-AF-004 notice requires comparison with AFP's controlled form before use. No form identifier is invented, and typed signer names do not indicate signatures or payment approval.

The case heading distinguishes pending edits, saving and locally saved data. Visible errors provide a reload action for the latest saved packet; active operations disable competing case actions. Empty states explain how to start and show when evidence is absent. The final review status distinguishes information awaiting comparison from information compared and awaiting AFP review. Its accompanying copy states that completed comparison is not payment approval. Word draft/template actions sit with the voucher, and the combined PDF action sits with the case summary and evidence status.

## Exports and authority

The combined PDF includes a case summary, evidence index with output page ranges, an optional FM-AF-014 draft and the selected source pages in their chosen order. Original PDF page contents remain vector/text where supplied; image sources are fitted to A4. Interactive PDF actions are removed while visible annotations are retained; signed originals remain separate evidence and a merged copy is not a renewed digital signature.

Page selection assembles a document set; it is not a PDF redaction or metadata-removal tool. Sensitive content must be removed from a separate source copy with an appropriate redaction workflow before that copy is added.

The Word actions export either the current editable draft or a blank template. Blank templates have no invented dates, people, amounts or signatures. The native PDF printer has JavaScript disabled, data-only pinned fonts and no network/file request access. None of these paths calls an AI provider or external OCR service.

Every export is labeled as a draft. `prepared-for-afp` means the listed case/source information has been compared, not that the required evidence or current financial policy has been verified. `paymentApproved` and `policyVerified` remain false. Required attachments depend on the current AFP source and expense scenario.

Workflow references: `docs/knowledge/qp-af-003.md` section 4.2 and `docs/knowledge/qp-af-004.md` Finance procedure. AFP reviews and prepares disbursement vouchers; authorized people approve and execute payments.

## AFP disbursement draft

The draft selector offers an AFP disbursement voucher separately from FM-AF-014. Its working layout follows the amount/payee/payer/checker/approver fields and Finance procedure in QP-AF-004. No controlled form identifier or revision has been confirmed for this layout; the UI and both exports explicitly require comparison with AFP's controlled form. Printed signer names never count as signatures or approval.

The draft records a human-entered date/number/reference, payment method, optional account/budget code, item gross amounts and evidenced deductions. The application never issues a voucher number, infers a tax rate, assumes a blank deduction is zero or initiates banking. Net amounts use decimal satang arithmetic; a deduction above its own item's gross is flagged even when the overall total could still balance. Unknown deductions leave the net amount pending.

Importing a checked FM-AF-014 is explicit and source-bound. It seeds only the payee and gross item data, leaving the new date, deductions and comparison open. Subsequent imports retain clerical edits and manually entered deductions. Source changes, payee/gross differences and case-content edits invalidate or flag the comparison. The PDF index accounts for both optional drafts before the selected evidence pages. Legacy v1 packets receive blank additive fields without erasing existing records. The Word actions export the current draft or a blank template without the case's personal or project data.

`node test/afp-payment-voucher-smoke.mjs` checks the real renderer/IPC migration, explicit import, unknown deductions, net amount, source changes, manual preservation, restart persistence and native Word/combined-PDF exports with synthetic data only. Controlled-form acceptance and real AFP operations are separate from these checks.

## Activity and supporting-evidence guidance

The packet infers a tentative activity only from its locally stored title and purpose. Ambiguous or unknown results remain unselected, and the employee can override them. The finance scenario is always chosen explicitly; an activity name never determines category B. A separate speaker choice can also be corrected. The review list ties FM-AF-015/019 and the employee receipt-replacement form to QP-AF-003 only when applicable, and shows the AFP circular's category B advance/settlement items only for the selected scenario.

The expense category (ยังไม่แน่ใจ, หมวด B, BV, ฉุกเฉิน, อื่น) is a separate choice from how the money moves, and uses the same labels as the receipt check. A receipt added with `เพิ่มใบเสร็จที่ตรวจแล้ว` carries the category the employee kept on the receipt check, plus the sub-category code when the suggestion matched it. It fills the packet category only while that is still `ยังไม่แน่ใจ`; a receipt checked under a different category is named under the category line and never overwrites it. Packets saved before the category existed read a หมวด B finance choice as category B. Besides advance (ยืมเงิน) and settlement (เคลียร์เงินยืม), the finance choice covers paying with one's own money first (QP-AF-003 section 4.3): `สำรองจ่ายเอง — ขออนุมัติก่อนจ่าย` lists FM-AF-002 and FM-AF-003 (4.3 a), and `สำรองจ่ายเอง — ขอเบิกคืน` lists FM-AF-002, FM-AF-003, the receipt, the payee identity alternatives and the approval report (4.3 b, which follows 4.2 a without the 4.1 loan agreement). The approval-report reason states 3 working days for category B and 5 for emergency, and is left out for `หมวดอื่น`.

`ยอดรวมตามหมวดย่อย` sums the amounts of receipts added from the receipt check, grouped by sub-category (B9.1 and B9.2 share B9; BV1 and BV2 are BV), because the circular caps category B at 10,000 baht per sub-category over all items, not per receipt. Only pages classified as receipts, tax invoices, cash bills or FM-AF-014 count, so an invoice or slip for the same purchase is not added twice. A category B group over 10,000 baht is marked over the cap. A group without a sub-category, or BV (capped per driver per activity), is only marked for checking. Unreadable amounts are counted separately. The same totals print on the packet cover. The totals are a review aid and do not decide eligibility. CV and privacy-notice suggestions are labeled as needing confirmation rather than financial requirements. The controlled source and AFP remain authoritative.

Page types may be assigned separately in mixed PDFs. Filenames can suggest one unambiguous type for unclassified pages, payment documents included (ใบเสร็จ, ใบกำกับภาษี, บิลเงินสด, ใบแจ้งหนี้, สลิป), but never verify contents or mark a page checked. `เพิ่มเอกสาร` takes several files at once and skips any whose content is already in the packet, naming them, instead of refusing the whole batch. A receipt whose file is already in the packet and is then compared on the receipt check is linked to that file by `เพิ่มใบเสร็จที่ตรวจแล้ว` (its values, category and type), not refused as a duplicate. Receipts with no category on the receipt or the packet are still summed under `ยังไม่ระบุหมวด`, marked as not yet compared with a cap. Checklist states distinguish a filename hint, a typed page awaiting review, a reviewed selected page, and no matching selected page. Staff may add, edit and remove their own items and link each to a local source; deleting a source clears its link without deleting the item. Changes to guidance, source documents, page inclusion, classifications or page review invalidate a previously checked disbursement draft. The combined PDF summary records these contextual prompts and their states, with no policy-completeness or payment-approval claim. Lists and manual links do not replace source inspection or MIS processes.

The optional AI handoff is separately previewed and explicitly initiated. It carries fixed labels for activity, finance scenario, speaker indication and document-type states. The employee may type additional general context, which must pass an always-on local privacy scan and masking before it appears in the preview; changing that text requires another scan. Known sensitive data with identifiers is blocked, and incomplete masking is withheld. Pattern scanning does not reliably identify every name or sensitive detail, so the employee must inspect and remove personal information from the preview. No title, purpose, filename, custom item label, page content or attachment is added automatically. The existing receipt handoff and chat consent path then applies. The answer is advice for review and does not automatically change the case, classify pages, approve payment or submit to MIS. The local checklist works without a provider. Synthetic tests do not establish live-provider performance or AFP acceptance.

## Claim interview

A blank packet (category `ยังไม่แน่ใจ` and finance `ยังไม่ทราบ`) opens a short interview at the top of the case chat (`src/claim-interview.ts` holds the rules, `src/claim-interview-panel.tsx` the chat). It asks one question at a time: what the expense is, what kind of work it was for, whether it is already paid, where the money comes from (advance, own money, unsure), the rough amount and the receipt date. The date is asked only once the employee has paid. Each question has quick-answer chips, and answers typed in the case chat's composer are read on the device (expense words, yes/no, amounts, Thai dates); an answer that reads as two expense types, or as nothing, asks again instead of guessing. "ทำไมต้องถาม" or a typed "ทำไม…" shows why that question matters, with its source (AFP circular section 3, QP-AF-003 4.2 a, and so on). A recommendation appears only when the packet title names the expense or activity, or for funding when the employee has not paid yet (AFP advises against paying first). It is shown, never selected for them.

Expense types map to the circular's categories: drinking water B10, venue, equipment, signage, photographer or MC B1, materials B9, hired or rented vehicles BV, an urgent repair to emergency. Food, lodging, travel, speakers and anything else map to `หมวดอื่น`. Their notes carry only what the knowledge base states (lodging per-room caps and Folio, travel at actual cost, one speaker per talk with 50 minutes counted as one hour) and say plainly that meal and speaker rates are not in the system's documents, so the employee should ask AFP. The summary card shows the category code, the approval-report deadline (3 working days after the receipt date for category B, 5 for emergency, weekends skipped, public holidays not counted and said so), the documents from the same evidence checklist as the packet, and the notes. These are the 10,000 baht cap with procurement for larger hiring and no advance, prior team-lead approval for emergency, and "do not pay before approval" for own-money cases.

`ใช้กับชุดเอกสารนี้` sets the packet's category, finance scenario, activity, speaker flag and mode (`จ่ายแล้ว` or awaiting payment). It replaces the title only when it is still the default or empty. The interview then folds to one line ("ตอบแล้ว: เบิกค่าน้ำดื่ม · B10") that reopens it with the answers kept. While a summary waits to be applied, the step's continue button turns quiet so the page keeps one primary action. `ถาม AI ต่อ` sends a fixed-vocabulary prompt (answer labels, category, documents and deadline only, never title, purpose or files) into the case chat, not the main chat. The prompt tells the AI not to conclude that the claim is payable. If the case gets its category or finance case another way first (a proposal from the chat, or the form), the interview folds away. The interview is a guide. AFP and the controlled sources remain authoritative.

## Case chat

Each case has one chat of its own (`src/claim-case-chat.tsx`, rules in `src/claim-case.ts`). It is an ordinary task with `claimPacketId` set: `create` with a packet id returns that case's existing chat, switching it to the AI chosen now when it is idle. Such chats are kept out of the chat list, search, the palette and the main chat; they show only in their case. Typed text goes to the open interview question first. With an AI chosen, text that is not an answer, any question ("ไหม", "อย่างไร", "?") longer than a short "why", and everything after the interview goes to the AI in this case. Without an AI, the interview still works and the chat says how to connect one. `ถาม AI` in the evidence guidance also asks in the case chat.

Each send carries the case as `sourceText`: fixed labels and counts only (mode, category, finance case, activity, whether a title is filled, pages per document type, reviewed receipt totals per sub-category, and the evidence checklist with its status). The title, purpose, names and file names stay out; the person can type them in the chat, where the usual send checks apply. The run uses the normal send path: consent and the usage terms (the dialog sends back into the case), privacy review and masking, hooks, the knowledge search (with `เบิกจ่าย AFP` added to the search text) and the answer check. The host refuses Skills, document drafting, images, workflows, the coordinator, side questions and attachments for case chats, and routes them as general help so no Skill menu question appears. `CLAIM_CASE_RULE` in `electron/service.ts` tells the AI to answer from AFP documents with the section, never to say a claim is approved or payable, to ask one question at a time, and to end with a fenced `claim-update` JSON block when the employee states a case field.

The renderer reads only the last readable block in the latest answer. It keeps `title`, `project`, `purpose`, `mode`, `category`, `finance` and `activity`, accepts values only from the same fixed lists as the form (unknown keys such as amounts are dropped), and shows only fields that would change. The card `เสนอกรอกในเรื่องนี้` shows each field and value with `ใช้ข้อมูลนี้` and `ไม่ใช้`. Nothing changes until the person accepts. Accepting edits the case like the form does, so it saves and the evidence list follows. While a proposal waits, the panel's continue button turns quiet so the page keeps one primary action.

## Adding and reading files in the case

The case chat takes several files at once: drag PDF, PNG or JPG files onto the chat column, or use the paperclip in the case composer (the same picker as `เพิ่มเอกสาร`, which now reads its files too). A drop sends each file's bytes to `receiptPacketAdd` with `files`; the host checks the type, the 25 MB per-file and 100 MB per-case limits and that pictures decode, and never reads a path the window names. The dropped file's own path (from `webUtils.getPathForFile` in the preload), when there is one, is kept only so an export cannot overwrite the original. Files of another type are skipped with their names in a notice, and files already in the case are skipped as before.

Each new file is then read on this computer, one at a time (`receiptPacketRead`): the PDF's own text first, then the local OCR if it is running. No AI is asked, and the text never leaves the main process; only the kind and the title words that decided it come back. `src/evidence-reading.ts` picks the kind whose title appears first in the opening 4,000 characters (`ใบเสร็จรับเงิน/ใบกำกับภาษี` together reads as the tax invoice, and the evidence forms such as `FM-AF-015` use the same words as the file-name hints). The card `อ่านไฟล์ที่เพิ่ม` shows each file's result: the kind and the word found, `ไม่พบหัวเอกสารที่รู้จัก`, or for a picture without local OCR, that OCR is not on. `ใช้ประเภทที่อ่านได้` sets the read kinds on those files' unclassified pages only, unchecked; pages the person typed keep their kind, and every page still needs its check against the original. Reading results stay in the window for this session and are not saved with the case.
