# ขั้นตอนการเขียนโค้ดและ Git

## Purpose

ทำหรือทบทวนการแก้ไขโค้ดที่มีขอบเขตชัดเจน พร้อมการตรวจที่ตรงจุดและการส่งต่องาน Git อย่างปลอดภัย

ร่างเริ่มต้น 14 กันยายน 2569 เจ้าของด้านเทคนิคและข้อตกลงเฉพาะโครงการ: รอยืนยัน ใช้กับ Developer และ Maintainer ไม่ได้กำหนดให้พนักงานทั่วไปต้องใช้ Git เพื่อเสนอแนวคิด Skill

## เมื่อควรใช้

- ต้องแก้ไขโค้ดในขอบเขตที่ระบุได้
- ต้องทบทวน diff หรืออธิบายผลกระทบของการแก้ไข
- ต้องรันการตรวจ เช่น test, lint, type check หรือ build

**Anti-trigger:**
- งานที่ทำเฉพาะบน GitHub เช่น PR, CI, merge ให้ใช้ `github-workflow`
- การ deploy ให้ใช้ `vercel-deploy`

## Inputs

- คำขอและขอบเขตที่ต้องการแก้
- repository หรือไดเรกทอรีที่ทำงาน
- ข้อตกลงของโครงการ เช่น คำสั่ง test, coding convention

**กำหนดโหมดตามคำขอ:**
- วางแผน อธิบาย หรือทบทวน → ตรวจสอบและรายงาน ห้าม implement หรือเปลี่ยนระบบภายนอก
- Implement หรือแก้ไข → แก้เฉพาะขอบเขตในเครื่องและตรวจสอบผล
- Publish, Merge หรือ Deploy → ทำเฉพาะรายการที่ผู้ใช้สั่งชัดเจน และต้องผ่านการอนุมัติกับการตรวจที่เกี่ยวข้อง

## Source

- คำแนะนำของ Repository เป็นแหล่งกำหนดข้อตกลงหลัก
- [ความปลอดภัยของ Secret](../../../rules/secret-safety.md) และ [การอนุมัติโดยมนุษย์](../../../rules/human-approval.md)
- [GitHub Protected Branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) เข้าถึงเมื่อ 14 กันยายน 2569 — เป็นความสามารถที่ตั้งค่าได้ ไม่ใช่หลักฐานว่า repository นี้เปิดใช้แล้ว

## Workflow

1. ค้นหารากของ Repository และตรวจสถานะกับ diff หากมี Git หากเป็นไดเรกทอรีทั่วไป ให้รายงานและทำงานในเครื่องต่อโดยไม่เริ่มต้น Git เว้นแต่ผู้ใช้ร้องขอ
2. ตรวจไฟล์ต้นฉบับที่เกี่ยวข้อง manifest ของ dependency test ที่มีอยู่ และคำสั่งที่ตั้งค่าไว้ ใช้ข้อตกลงของโครงการแทนการกำหนดภาษา framework หรือ package manager เอง
3. ระบุพฤติกรรมที่ต้องการและเกณฑ์การยอมรับ จำลองปัญหาก่อนแก้เมื่อทำได้
4. แก้ไขให้น้อยที่สุดแต่ครบเป็นเรื่องเดียว และรักษาการแก้ไขเดิมของผู้ใช้ หากทับซ้อนกับสิ่งที่ต้องทำ ให้หยุดและถามวิธีจัดการ
5. รัน test, lint, type check หรือ build ที่มีและเกี่ยวข้องตามผลกระทบ สำหรับ Harness นี้ ให้รัน `python scripts/validate_repo.py` เมื่อแก้ Skill หรือ configuration
6. ทบทวน diff สุดท้ายเพื่อหาไฟล์ที่เปลี่ยนโดยไม่ตั้งใจ secret ไฟล์ที่สร้างขึ้น และการถดถอยของพฤติกรรม แยกปัญหาที่มีอยู่ก่อนออกจากปัญหาใหม่ด้วยหลักฐาน
7. รายงานไฟล์ที่เปลี่ยน ผลการตรวจ ความเสี่ยงที่เหลือ และการดำเนินการถัดไป

สำหรับการแก้ไข UI ให้ตรวจพฤติกรรมที่ render แล้วเมื่อมีเครื่องมือ สำหรับ data migration หรือการเปลี่ยนแปลงที่ทำลายข้อมูล ให้ยืนยันเป้าหมาย แผนกู้คืน และการอนุมัติที่จำเป็นก่อนดำเนินการ

**การส่งต่องาน Git** — ตรวจ rules ของ repository ก่อนเลือกชื่อ branch รูปแบบ commit หรือวิธี merge ใช้ภาษาอังกฤษสำหรับชื่อ branch ข้อความ commit ข้อความ pull request และ code comment เว้นแต่ผู้ใช้สั่งเป็นอย่างอื่น stage เฉพาะการเปลี่ยนแปลงที่ตั้งใจ และตรวจ staged diff ก่อน commit ที่ได้รับอนุญาต

## Output

- ผลลัพธ์และขอบเขตงาน
- ไฟล์ที่เปลี่ยนหรือผลตรวจพร้อมตำแหน่ง
- การตรวจสอบ: คำสั่ง ผลที่พบ และข้อจำกัด
- ความเสี่ยงที่ทราบและแนวทางกู้คืนเมื่อเกี่ยวข้อง
- สถานะ Git และการดำเนินการที่ทำจริง โดยแยกสถานะ deploy ออกมาต่างหาก

**ตัวอย่างและเกณฑ์ตรวจรับ**

- ผู้ใช้ขอแผน: ส่งแบบออกแบบและกลยุทธ์ test โดยไม่ implement
- ผู้ใช้ขอแก้ unit test ที่ล้มเหลว: ตรวจพฤติกรรม แก้โค้ดหรือ test ที่เกี่ยวข้อง รันการตรวจเฉพาะจุด และรักษาการแก้ไขที่ไม่เกี่ยวข้อง
- เปลี่ยน Skill ใน Harness นี้: ตรวจ frontmatter และ reference แยกผลตรวจโครงสร้างออกจากการทดสอบพฤติกรรม
- ไม่มีข้อมูล Git: การแก้ไขในเครื่องอาจเสร็จได้ แต่ห้ามอ้างว่ามี commit หรือ branch
- CI ที่จำเป็นล้มเหลว: รายงานเป็นตัวขัดขวาง ห้ามปิด check เพื่อให้ merge ได้

## Authority

AI ช่วยได้: แก้โค้ดในขอบเขตที่ขอ รันการตรวจ และรายงานผล

ต้องให้มนุษย์ตัดสิน:
- การ merge, deploy production และการเปลี่ยน branch protection
- การรัน migration ที่กระทบข้อมูลจริง
- การยกเว้น check ที่ล้มเหลว

**คำขอให้เขียนโค้ดไม่ใช่การอนุญาตให้ deploy production หรือทำความสะอาดไฟล์ที่ไม่เกี่ยวข้อง**

## Handoff

- commit, PR และ merge → `github-workflow`
- deployment → `vercel-deploy`
- การสื่อสารการเปลี่ยนแปลงต่อผู้ใช้ → `step-writing`

พร้อมส่งต่อเมื่อ: diff ผ่านการทบทวน ผลการตรวจมีหลักฐาน และระบุความเสี่ยงที่เหลือแล้ว

## Guardrails

- ห้ามอ้างว่า test ผ่านหากยังไม่ได้รัน ให้ระบุการตรวจที่ทำไม่ได้
- ห้าม reset งานของผู้ใช้ force push เปลี่ยน branch protection หรือข้าม check ที่ล้มเหลว หากยังไม่มีอำนาจชัดเจน
- ห้าม commit secret, token หรือ private runtime state
- แยกปัญหาที่มีอยู่ก่อนออกจากปัญหาใหม่ด้วยหลักฐาน

## แหล่งที่มาและการนำไปใช้

อ้างอิง rules และขั้นตอนภายในที่เชื่อมโยงไว้ ตรวจทานเมื่อ 14 กันยายน 2569 ก่อนนำไปใช้ เจ้าของด้านเทคนิคควรยืนยันคำสั่ง test ข้อกำหนดการตรวจทาน ข้อตกลงเรื่อง branch และอำนาจ deploy ของแต่ละ repository
