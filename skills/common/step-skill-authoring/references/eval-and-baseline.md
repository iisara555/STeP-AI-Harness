# Eval และ Baseline สำหรับ Skill ของ STeP

เปิดไฟล์นี้เมื่อจะสร้าง Skill ใหม่ ปรับ Skill เดิมอย่างมีนัยสำคัญ หรือเขียน eval ให้ Skill ที่ยังอยู่ใน `legacyWithoutEvals`

## 1. เริ่มจากเคสที่พลาด (RED → GREEN)

ก่อนเขียนหรือแก้ Skill ให้มีหลักฐานว่า AI ทำพลาดเมื่อไม่มีการเปลี่ยนแปลงนี้:

1. เลือกคำขอจริงหรือจำลอง 1–3 ข้อที่ Skill ต้องทำให้ดีขึ้น
2. ดูว่าคำตอบแบบไม่มี Skill (หรือ Skill รุ่นเดิม) พลาดตรงไหน แล้วเขียนลงในฟิลด์ `baseline.withoutSkillTypicallyMisses`
3. เขียนหรือแก้ Skill ให้น้อยที่สุดที่แก้จุดพลาดนั้น
4. รันเคสเดิมอีกครั้ง ถ้าไม่ดีขึ้น แปลว่าการแก้ยังไม่ตรงปัญหา

Skill ที่เขียนโดยไม่เคยเห็นเคสที่พลาด มักสอนสิ่งที่โมเดลทำได้อยู่แล้ว ซึ่งเพิ่ม context โดยไม่เปลี่ยนผลลัพธ์

## 2. ไฟล์ eval

ทุก Skill ใหม่ต้องมี `evals/skills/<skill>.json` ที่ root ของ repository (ไม่ถูกแจกไปกับชุดติดตั้ง) และมีเคสครบ 4 มิติ:

| มิติ | ตรวจอะไร | `expect` ที่ต้องมี |
| --- | --- | --- |
| `positive` | คำขอที่ควรเข้า Skill นี้ | `mode`, `skill` และ `outputAssertions` |
| `antiTrigger` | คำขอคล้ายกันที่ต้องไม่เข้า Skill นี้ | `notSkill` เป็นชื่อ Skill นี้ หรือ `mode: PLAYBOOK` |
| `collision` | คำขอที่ชนกับ Skill ข้างเคียง | `skill` ปลายทางที่ถูก และ `notSkill` |
| `missingSource` | เมื่อข้อมูลหรือกฎที่ต้องใช้ไม่มี | `mode`, `skill` และ `outputAssertions` ว่าต้องเปิดเผยช่องว่าง ไม่แต่ง |

`test/skill-evals.test.js` รันส่วน routing ของทุกเคสใน CI ส่วน `outputAssertions` เป็นเกณฑ์ตรวจคำตอบของโมเดล ซึ่ง CI ไม่ได้รัน

Assertion ที่ดี:

- ตรวจได้จริงจากคำตอบ เช่น "อ้างข้อ 4.4" ไม่ใช่ "ตอบได้ดี"
- อ่านแล้วรู้ทันทีว่าตรวจอะไร
- **แยกได้:** ถ้า assertion ผ่านทั้งแบบมี Skill และไม่มี Skill แปลว่าไม่ได้วัดคุณค่าของ Skill ให้เปลี่ยนเป็นข้อที่แยกได้

## 3. เทียบกับ baseline

เมื่อรันแบบ model-side ให้รันคำขอเดียวกันสองแบบในรอบเดียวกัน:

- **มี Skill** เทียบกับ **ไม่มี Skill** สำหรับ Skill ใหม่
- **Skill รุ่นใหม่** เทียบกับ **รุ่นก่อนแก้** สำหรับการปรับ Skill เดิม

ให้ผู้ตรวจ (คนหรือ AI อีกตัวที่ไม่ได้เขียน Skill) ให้คะแนน assertion ทั้งสองแบบ แล้วบันทึกผลและวันที่ใน `baseline.modelSideRun`
ถ้าไม่มีสภาพแวดล้อมที่แยกตัวตรวจได้ ให้บันทึกว่าเป็นการตรวจโดยผู้เขียนเอง ซึ่งเชื่อถือได้น้อยกว่า

## 4. ตัวอย่างผลลัพธ์

ทุก Skill ใหม่ต้องมีโฟลเดอร์ `examples/` ที่มีตัวอย่างคำตอบที่ดีอย่างน้อยหนึ่งไฟล์:

- ใช้ข้อมูลสังเคราะห์ เพราะ repository เป็น Public
- มีคำขอ คำตอบ และหัวข้อ "ทำไมคำตอบนี้ดี" ที่ชี้พฤติกรรมที่ต้องการ
- ถ้าตัวเลขมาจากเอกสารอ้างอิง ให้บอกว่าต้องยึดเอกสารปัจจุบัน ไม่ใช่ตัวเลขในตัวอย่าง
- เชื่อมจากหัวข้อ Output ของ SKILL.md พร้อมบอกว่าเปิดเมื่อไร

## 5. หนี้ที่บันทึกไว้

Skill ที่มีก่อนกลไกนี้อยู่ใน `legacyWithoutEvals` ของ `manifest/skill-evals.json` รายการนี้ลดได้อย่างเดียว:

- เพิ่ม eval ให้ Skill ใด ต้องลบ Skill นั้นออกจากรายการในการเปลี่ยนแปลงเดียวกัน
- Skill ใหม่เข้ารายการนี้ไม่ได้ test จะล้มถ้าขนาดรายการเกิน `legacyCeiling`
