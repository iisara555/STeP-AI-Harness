# Stakeholder Questionnaire

## Purpose

เปลี่ยนสิ่งที่งานยังขาดให้เป็น **ชุดคำถามที่ส่งให้คนที่รู้คำตอบได้ทันที** เพื่อให้ได้คำตอบในรอบเดียว แทนการรอหรือถามทีละข้อผ่านแชต

ใช้ได้ทั้งตอนที่ Skill อื่นหยุดที่ `รอยืนยัน` เพราะ Source ยังไม่ครบ และตอนที่ต้องเก็บข้อมูลจากเจ้าของโจทย์ก่อนเริ่มงาน

## เมื่อควรใช้

- Skill อื่นตอบว่าเอกสารหรือเงื่อนไขยัง `รอยืนยัน` และผู้ใช้ต้องถามเจ้าของเอกสาร
- ต้องขอคำยืนยันจากทีมอื่นก่อนตัดสินใจหรือเริ่มงาน เช่น AFP, QS, HD หรือหน่วยงานภายนอก
- เจ้าของโจทย์หรือหัวหน้ามีข้อมูลที่ผู้ใช้ไม่มี และต้องการรวบรวมคำถามไปถามครั้งเดียว

**Anti-trigger:**
- แบบสำรวจความพึงพอใจหรือแบบประเมินผู้เข้าร่วมงาน → ไม่ใช่งานของ Skill นี้ ให้ช่วยแบบงานทั่วไป หรือ `voice-of-customer` เมื่อวิเคราะห์ความเห็นลูกค้าที่เก็บมาแล้ว
- สัมภาษณ์ลูกค้าเพื่อทดสอบสมมติฐานธุรกิจ → `startup-discovery`
- ถามสิทธิ์ HR หรือระยะเวลา AFP ที่มีในดัชนีแล้ว → `hr-policy-lookup` หรือ `afp-operations-lookup` ให้ตอบจากดัชนีก่อน แล้วค่อยใช้ Skill นี้กับส่วนที่ดัชนีไม่มี
- ร่างหนังสือราชการขอข้อมูล → `thai-official-documents` (Skill นี้ใช้ร่างชุดคำถามที่แนบไปกับหนังสือได้)

## Inputs

ขั้นต่ำ:
- เรื่องที่ติดอยู่ และการตัดสินใจหรืองานที่รอคำตอบนี้

ถามผู้ใช้**เฉพาะเรื่องการส่ง** ซึ่งผู้ใช้ตอบได้เสมอ ในข้อความเดียว:
1. ส่งถึงใคร (บทบาทหรือทีม) และเขารู้อะไรที่ผู้ใช้ไม่รู้
2. ต้องได้อะไรกลับมาบ้าง เพื่อตัดสินใจหรือทำงานต่อได้

ถ้าข้อความผู้ใช้หรือผลของ Skill ก่อนหน้าตอบสองข้อนี้แล้ว ไม่ต้องถามซ้ำ

## Source

- คำถามมาจาก **ช่องว่างระหว่างสิ่งที่ผู้รับรู้กับสิ่งที่ผู้ใช้ต้องการ** ไม่ใช่จากความรู้ทั่วไปของ AI
- ถ้าเริ่มจากผล `รอยืนยัน` ของ Skill อื่น ให้ใช้รายการ issue ใน routing contract หรือคำตอบของ Skill นั้นเป็นต้นทาง และอ้าง id เอกสารจาก `manifest/documents.yaml` ในคำถาม
- ไม่มี Source ภายนอกอื่นที่จำเป็น

## Workflow

1. **ระบุผู้รับ** ครบเมื่อรู้บทบาทของผู้รับ และรู้ว่าเขาถือข้อมูลอะไรที่ผู้ใช้ไม่มี
2. **ระบุสิ่งที่ต้องได้กลับ** ครบเมื่อได้รายการการตัดสินใจหรือข้อเท็จจริงที่ต้องมีเพื่อทำงานต่อ
3. **เขียนคำถาม** ตามโครงใน Output เรียงจากสำคัญที่สุด เพราะผู้รับอาจตอบเพียงรอบเดียว
4. **ตรวจความครบ** ทุกรายการในข้อ 2 ต้องมีคำถามรองรับอย่างน้อยหนึ่งข้อ และทุกคำถามต้องมีเหตุผลว่าคำตอบจะเอาไปใช้ทำอะไร
5. **ส่งคืนผู้ใช้เป็นร่าง** ผู้ใช้เป็นคนส่งเองผ่านช่องทางของทีม

## Output

ตัวอย่างคำตอบที่ดีพร้อมเหตุผล (ข้อมูลสังเคราะห์): [examples/good-output.md](examples/good-output.md) เปิดดูเมื่อไม่แน่ใจรูปแบบ

```markdown
# [หัวข้อที่ต้องการคำตอบ]

**ใช้เพื่อ:** [การตัดสินใจหรืองานที่รอคำตอบนี้]
**จาก:** [ผู้ใช้/ทีม] **ถึง:** [ผู้รับ] **คำตอบจะนำไปใช้:** [ที่ไหน อย่างไร]

## บริบท
[หนึ่งย่อหน้า พอให้ผู้รับที่ไม่ได้อยู่ในเรื่องตอบได้ถูก]

## วิธีตอบ
[กำหนดส่งและเวลาที่ใช้โดยประมาณ] ตอบบางข้อหรือตอบว่า "ไม่แน่ใจ" ได้ ช่วยบอกข้อที่ไม่แน่ใจแทนการข้าม

## [หมวดคำถาม]
### [คำถามหนึ่งเรื่องต่อหนึ่งข้อ]
_ทำไมต้องถาม: [ใส่เฉพาะเมื่อคำถามอาจถูกเข้าใจผิดหรือถูกตอบแบบผ่าน ๆ]_
> คำตอบ:

## มีอะไรที่เราไม่ได้ถามแต่ควรรู้ไหม
> คำตอบ:
```

- คำถามหนึ่งข้อถามเรื่องเดียว ไม่ถามซ้อน
- จัดเป็นหมวดเมื่อมีมากกว่า 5 ข้อ
- ถ้าเกิน 10 ข้อ ให้แยกข้อที่ไม่จำเป็นต่อการตัดสินใจรอบนี้ออกไปไว้รอบถัดไป

## Authority

AI ช่วยได้: วิเคราะห์ช่องว่าง ร่างและจัดลำดับคำถาม

ต้องให้มนุษย์ทำ:
- ส่งคำถามถึงผู้รับ และเลือกช่องทางการส่ง
- ตีความคำตอบที่มีผลต่อระเบียบ การเงิน หรือการอนุมัติ ซึ่งผู้มีอำนาจตาม `manifest/authority.yaml` ต้องยืนยัน

## Handoff

- ต้องส่งเป็นหนังสือราชการ → `thai-official-documents` แนบชุดคำถามนี้
- ได้คำตอบที่เป็นเอกสารหรือระเบียบฉบับใหม่ → แจ้งผู้ดูแลระบบให้ลงทะเบียนใน `manifest/documents.yaml` ก่อน Skill อื่นจะอ้างได้
- ได้คำตอบแล้วต้องกลับไปทำงานเดิม → Skill ที่หยุดที่ `รอยืนยัน` เดิม

พร้อมส่งต่อเมื่อ: ทุกสิ่งที่ผู้ใช้ต้องได้กลับมีคำถามรองรับ และผู้รับตอบได้โดยไม่ต้องถามกลับ

## Guardrails

- เขียนคำถามถึงสิ่งที่ผู้รับรู้ ไม่ถามสิ่งที่ผู้ใช้หรือเอกสารในระบบตอบได้อยู่แล้ว
- ไม่ใส่ข้อมูลส่วนบุคคลหรือข้อมูลภายในที่ผู้รับไม่จำเป็นต้องเห็น ตาม `rules/data-classification.md`
- ไม่เขียนคำถามชี้นำให้ผู้รับยืนยันสิ่งที่ผู้ใช้อยากได้
- ไม่ถือว่าคำตอบในแชตเป็นการยืนยันระเบียบ จนกว่าเจ้าของเอกสารจะยืนยันผ่านช่องทางของทีม
