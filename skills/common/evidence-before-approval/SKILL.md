# STeP Evidence Before Approval

## Purpose

เป็น **verification layer** ที่ตรวจว่าข้อกล่าวอ้างว่างาน "เรียบร้อย ถูกต้อง พร้อมส่ง" มีหลักฐานรองรับจริงหรือไม่

หลักสำคัญ: **Evidence before assertion** — ความสำเร็จของขั้นตอนหนึ่งไม่ใช่หลักฐานว่าผลลัพธ์ถูกต้อง

ใช้ร่วมกับ Skill เฉพาะงาน เช่น TOR, Finance, QS, Document, Project หรือ Creative ไม่ใช่ตัวแทนการตรวจเชิงโดเมนทั้งหมด

## เมื่อควรใช้

- ผู้ใช้ถามว่า "พร้อมส่งไหม", "ครบหรือยัง", "ยืนยันได้ไหม", "ปิดงานได้หรือยัง"
- AI กำลังจะสรุปว่า task สำเร็จ แก้ไขแล้ว ผ่านแล้ว หรือพร้อมใช้งาน
- ต้องตรวจหลักฐานก่อน handoff, submit, publish หรือ review รอบมนุษย์

**Anti-trigger:**
- การอนุมัติงบประมาณ จัดซื้อ ลงนาม ประกาศใช้ SOP หรือการตัดสินทางกฎหมาย เป็นอำนาจมนุษย์
- การตรวจมาตรฐานเฉพาะทางที่มี Skill เจ้าของโดเมนอยู่แล้ว ให้ใช้ Skill นั้น

## Inputs

ขั้นต่ำ:
- ข้อกล่าวอ้างที่ต้องการตรวจ
- งานหรือเอกสารที่เกี่ยวข้อง

ถ้าไม่มี access ถึงหลักฐาน ให้ระบุ `UNVERIFIED` และบอกสิ่งที่ต้องตรวจ ไม่เดา

## Source

- หลักฐานต้องมาจาก source จริง เช่น ไฟล์ ผลการรัน checklist หรือ record
- **ห้ามสร้าง evidence, test result, citation หรือ approval ขึ้นเอง**
- ถ้าข้อกล่าวอ้างอ้างถึงระเบียบ ให้ resolve จาก `manifest/documents.yaml`

## Workflow

1. **ระบุ Claim** — เขียนให้ชัดว่ากำลังจะยืนยันอะไร เช่น "เอกสารมีหัวข้อครบตาม template", "ตัวเลขในตารางรวมถูกต้อง", "ไฟล์ export เปิดได้", "ข้อแก้ไขจากรอบก่อนถูกดำเนินการครบ" **ห้ามใช้คำกว้างว่า "โอเคแล้ว" โดยไม่มี claim ที่ตรวจได้**
2. **ระบุ Evidence ที่ต้องมี** — จับคู่ทุก claim กับหลักฐานโดยตรง: ความครบถ้วน → checklist หรือ source template, ตัวเลข → สูตร source data หรือการคำนวณซ้ำ, ไฟล์ → เปิดไฟล์จริงหรือ validation result, การแก้ไข → diff, before-after หรือ issue list
3. **ตรวจ Source และ Freshness** — หลักฐานมาจากแหล่งไหน เป็นข้อมูลล่าสุดพอสำหรับ claim นี้หรือไม่ เป็นข้อมูลจริงหรือสมมติฐาน และมีข้อจำกัดหรือ sample bias หรือไม่
4. **Cross-check** — เมื่อ claim สำคัญ ให้ตรวจอย่างน้อยหนึ่งทางที่เป็นอิสระจากขั้นตอนสร้างงาน เช่น คำนวณซ้ำ ตรวจจาก source ต้นฉบับ หรือเทียบ checklist
5. **ให้สถานะ** — ใช้ 3 สถานะเท่านั้น: **VERIFIED** (มีหลักฐานตรงกับ claim), **PARTIAL** (ตรวจได้บางส่วน ยังมี gap ชัดเจน), **UNVERIFIED** (ยังไม่มีหลักฐานพอ ห้ามกล่าวว่าเสร็จหรือผ่าน)

## Output

### Verification Summary

- **Claim**
- **Status:** VERIFIED / PARTIAL / UNVERIFIED
- **Evidence checked**
- **Gap / risk**
- **Next verification**
- **Human decision required:** Yes / No

ถ้ามีหลาย claim ให้ใช้ตารางสั้น ๆ แทนการเขียนยาว

## Authority

AI ช่วยได้: ตรวจความพร้อมและระบุ gap

ต้องให้มนุษย์ตัดสิน:
- การอนุมัติทุกประเภทตาม `manifest/authority.yaml`
- การประกาศว่าเอกสารหรืองานพร้อมใช้อย่างเป็นทางการ

**ถ้า claim อยู่ในอำนาจอนุมัติของมนุษย์ ตรวจความพร้อมได้ แต่ห้ามเปลี่ยนเป็นคำว่า "อนุมัติแล้ว"**

## Handoff

- หลัง verification ให้กลับไปยัง Skill เจ้าของงานเพื่อแก้ gap หรือจัดทำ final output
- ข้อมูลส่วนบุคคลหรือข้อมูลลับ → `data-privacy-compliance`
- gap ที่กลายเป็นข้อบกพร่องของระบบคุณภาพ → `ncr-capa`

พร้อมส่งต่อเมื่อ: ทุก claim มีสถานะ และ claim ที่ยัง UNVERIFIED ระบุวิธีตรวจต่อไว้แล้ว

## Guardrails

- ความสำเร็จของคำสั่งหรือการสร้างไฟล์ ไม่เท่ากับความถูกต้องของผลลัพธ์
- ห้ามสร้าง evidence, test result, citation หรือ approval ขึ้นเอง
- ถ้าไม่มี access ถึงหลักฐาน ให้ระบุ `UNVERIFIED` ไม่เดา
- ไม่ลดระดับ claim ให้ตรวจง่ายขึ้นเพื่อให้ผ่าน

## Method note

แนวคิด Evidence-before-assertion ได้แรงบันดาลใจจาก `verification-before-completion` ใน obra/superpowers (MIT) และเขียนใหม่สำหรับงานองค์กร STeP ที่ไม่จำกัดเฉพาะงานซอฟต์แวร์
