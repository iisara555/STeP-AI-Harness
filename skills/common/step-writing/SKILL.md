# STeP Writing

## Purpose

สร้างหรือปรับข้อความสำหรับการสื่อสารของ STeP จากข้อมูลที่ผู้ใช้หรือแหล่งข้อมูลให้มา

หน้าที่ของ Skill นี้คือ **Facts / Source → Communication-ready Draft** โดยปรับภาษา โครงสร้าง น้ำเสียง และระดับรายละเอียดให้เหมาะกับผู้รับสารและช่องทาง

## เมื่อควรใช้

- ต้องเขียนอีเมล ข้อความภายใน ประกาศ หรือส่วนของรายงาน
- ต้อง rewrite หรือ polish ข้อความเดิม
- ต้องปรับข้อความให้เหมาะกับผู้รับสารคนละกลุ่ม

**Anti-trigger:**
- ค้นหาข้อเท็จจริงที่ไม่มีในต้นทาง
- ตัดสินสถานะ การอนุมัติ หรือผู้รับผิดชอบแทนผู้ใช้
- หนังสือราชการตามแบบฟอร์ม → `thai-official-documents`
- เรื่องน้ำเสียงตามช่องทางและการตรวจข้อเท็จจริงก่อนเผยแพร่ → `brand-tone-of-voice`

## Inputs

อาจได้รับ: ข้อเท็จจริงหรือ bullet points, draft เดิม, meeting output, project update, รายงานหรือเอกสารต้นทาง, action items หรือข้อความที่ต้องการเขียนใหม่

พร้อมบริบทเท่าที่มี: ผู้รับสาร, วัตถุประสงค์, ช่องทาง, ความยาว และภาษาที่ต้องการ

ภาษาไทยเป็นค่าเริ่มต้นสำหรับงานภายใน STeP เว้นแต่ผู้ใช้ระบุเป็นอย่างอื่น

## Source

- ข้อเท็จจริงทั้งหมดต้องมาจาก **ต้นทางที่ผู้ใช้ให้มา**
- กฎองค์กรที่ต้องปฏิบัติตาม: `rules/step-writing.md`, `rules/data-classification.md`, `rules/human-approval.md`
- หากกฎเหล่านี้ขัดกับคำขอ ให้ถือกฎที่มี authority สูงกว่าเป็นหลัก

## Workflow

**Writing Modes** — เลือกเฉพาะรูปแบบที่ตรงกับคำขอ: Email, หนังสือหรือข้อความทางการ, Internal message, Report section, Executive communication, Announcement, Caption หรือ Public communication, Rewrite/Polish ไม่จำเป็นต้องใช้โครงสร้างเดียวกันทุกประเภท

1. ระบุผู้รับสาร วัตถุประสงค์ ช่องทาง และระดับความเป็นทางการจากคำขอ
2. แยกข้อมูลต้นทางเป็น ข้อเท็จจริงที่ยืนยันได้, action หรือ request ที่ระบุไว้ และข้อมูลที่ยังไม่ยืนยัน
3. รักษาข้อมูลสำคัญตามต้นฉบับ: ชื่อบุคคล ชื่อหน่วยงาน ชื่อโครงการ วันที่ จำนวนเงิน ตัวเลข รหัส ผู้รับผิดชอบ สถานะ และการอนุมัติ
4. เลือกโครงสร้างที่เหมาะกับช่องทาง ไม่บังคับ template เดียวกับทุกงาน
5. ปรับภาษาให้ชัดเจน กระชับ อ่านง่าย เหมาะกับผู้รับสาร และไม่เพิ่มความหมายเกินต้นทาง
6. ตรวจว่า draft สุดท้ายไม่มีข้อเท็จจริงใหม่ที่ไม่ได้รับการรองรับ
7. อ่านรอบสุดท้ายเพื่อตัดสำนวนที่ฟังออกว่า AI เขียน ตาม [references/thai-ai-writing-patterns.md](references/thai-ai-writing-patterns.md) ถ้าผู้ใช้ขอ "ให้ไม่เหมือน AI" หรือ "ให้เป็นธรรมชาติ" ให้ใช้รายการนี้ตรวจทั้งข้อความ

**หลักการเขียน**

- **สำคัญก่อน** — ถ้าข้อความมี action, decision หรือ deadline ให้สิ่งสำคัญมองเห็นได้เร็ว แต่ไม่จำเป็นต้องขึ้นต้นด้วย action ทุกกรณี เช่น caption หรือข้อความประชาสัมพันธ์
- **เขียนตามผู้รับสาร** — ปรับระดับรายละเอียดและศัพท์ตามกลุ่ม: ผู้บริหาร พนักงาน STeP ผู้ประกอบการ partner หน่วยงานภาครัฐ หรือบุคคลทั่วไป
- **รักษาความหมาย** — rewrite หรือ polish เปลี่ยนลำดับ ประโยค น้ำเสียง และความกระชับได้ แต่ **ห้ามเปลี่ยนข้อเท็จจริง สถานะ ความรับผิดชอบ deadline approval หรือ commitment**
- **Uncertainty** — ถ้าต้นทางไม่ชัด อย่าเติมเอง ใช้ถ้อยคำที่ไม่ทำให้สิ่งที่ยังไม่ยืนยันกลายเป็นข้อเท็จจริง และทำเครื่องหมายไว้ เช่น `[รอยืนยันวันที่]`

## Output

ตัวอย่างคำตอบที่ดีพร้อมเหตุผล (ข้อมูลสังเคราะห์): [examples/good-output.md](examples/good-output.md) เปิดดูเมื่อไม่แน่ใจรูปแบบ หรือเมื่อข้อมูลต้นทางไม่ครบ

ส่งข้อความที่พร้อมนำไปใช้ต่อเป็นผลลัพธ์หลัก ไม่ต้องอธิบายกระบวนการเขียน เว้นแต่ผู้ใช้ขอ

หากมีข้อมูลที่จำเป็นแต่ยังไม่ยืนยัน ให้เพิ่มท้ายผลลัพธ์:

### ข้อมูลที่ต้องยืนยัน
- …

หากไม่มีข้อมูลค้าง ไม่ต้องสร้างส่วนนี้

## Authority

AI ช่วยได้: ร่าง ปรับภาษา และชี้จุดที่ยังไม่ยืนยัน

ต้องให้มนุษย์ตัดสิน:
- การส่งและการเผยแพร่ทุกกรณี ตาม `rules/human-approval.md`
- การรับรองข้อเท็จจริง ตัวเลข และคำมั่นในข้อความ
- การสร้างข้อผูกพันในนาม STeP

## Handoff

- หนังสือราชการตามแบบฟอร์ม → `thai-official-documents`
- น้ำเสียงตามช่องทางและการตรวจข้อเท็จจริง → `brand-tone-of-voice`
- ตรวจเอกสารก่อนส่ง → `document-review`
- ข้อความที่มีข้อมูลส่วนบุคคล → `data-privacy-compliance`

พร้อมส่งต่อเมื่อ: ข้อเท็จจริงทุกข้อมาจากต้นทาง และรายการที่รอยืนยันถูกแยกให้เจ้าของงานเห็น

## Guardrails

- ห้ามสร้างชื่อ วันที่ ตัวเลข หรือรายละเอียดขึ้นเอง
- ห้ามกำหนด Owner หากต้นทางไม่ได้ระบุ
- ห้ามเปลี่ยน Proposal ให้กลายเป็น Decision
- ห้ามเปลี่ยน Planned ให้กลายเป็น Completed
- ห้ามเขียนเหมือนมีการอนุมัติแล้ว หากยังไม่มีหลักฐาน
- ห้ามสร้าง commitment ในนาม STeP โดยไม่มีข้อมูลรองรับ
- ห้ามทำให้สมมติฐานดูเป็นข้อเท็จจริง
- รักษาคำเฉพาะ ชื่อโครงการ และรหัสสำคัญตามต้นทาง
- หลีกเลี่ยงภาษาราชการที่ซับซ้อนเกินจำเป็น เว้นแต่รูปแบบเอกสารกำหนด
