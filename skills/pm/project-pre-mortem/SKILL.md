# STeP Project Pre-Mortem Engine

## Purpose

จำลองว่าโครงการล้มเหลวไปแล้วในอนาคต แล้วสืบหาสาเหตุย้อนกลับ เพื่อวางมาตรการสกัดกั้นตั้งแต่ก่อนเริ่มงานจริง ตามแนวคิด Pre-Mortem ของ Gary Klein

ใช้กับผู้จัดการโครงการ (PM), โครงการภาครัฐ (PubSec), ทีมเทคโนโลยีขั้นสูง (Tech Up), ถ่ายทอดเทคโนโลยี (Tech Spin) และโรงงานต้นแบบ (FOODFABR)

## เมื่อควรใช้

ใช้เมื่อผู้ใช้พูดในลักษณะ:
- "โครงการนี้อาจพังตรงไหนบ้าง"
- "ช่วยดักความเสี่ยงก่อนเซ็นสัญญา"
- "ทำ pre-mortem ให้โครงการนี้"
- "จำลองความล้มเหลวล่วงหน้า"

**Anti-trigger:**
- ต้องการแผนงาน งวดงาน หรือ Timeline ให้ใช้ `project-plan`
- ต้องการทบทวนความเสี่ยงและโอกาสของระบบคุณภาพ ให้ใช้ `qms-risk-opportunity-review`
- ต้องการตรวจข้อกำหนดใน TOR ให้ใช้ `tor-review`

## Inputs

ขั้นต่ำ:
- ขอบเขตโครงการหรือร่างสัญญาที่กำลังจะเริ่ม

ช่วยให้ผลแม่นขึ้นถ้ามี:
- แผนงานและงวดส่งมอบที่ร่างไว้
- ข้อจำกัดด้านงบประมาณ เวลา หรือทรัพยากรที่รู้อยู่แล้ว
- บทเรียนจากโครงการคล้ายกันที่เคยมีปัญหา

## Source

- แหล่งหลักคือ **เอกสารโครงการและประสบการณ์ของทีมที่เข้าร่วม**
- บทเรียนจากโครงการเก่าเป็น historical reference ไม่ใช่กฎ ต้องระบุว่าเป็นกรณีศึกษา
- ถ้าความเสี่ยงอ้างถึงระเบียบหรือเงื่อนไขแหล่งทุน ให้ resolve จาก Controlled Source ใน `manifest/documents.yaml`
- แม่แบบในโฟลเดอร์นี้: `templates/pre-mortem-matrix-template.md`

## Workflow

1. **ตั้งโจทย์จำลองความล้มเหลว** — ประกาศกับทีมว่า "โครงการนี้ไม่ผ่านการตรวจรับ เสียหาย และสร้างผลกระทบร้ายแรง" แทนการถามว่าอะไรอาจผิดพลาด
2. **ระดมสาเหตุ** — ให้ผู้เข้าร่วมเขียนต้นตอความล้มเหลวโดยไม่ปิดกั้น ครอบคลุมด้านเทคนิค จัดซื้อ บุคลากร แหล่งทุน และพันธมิตร
3. **จัดหมวดหมู่** ด้วย `templates/pre-mortem-matrix-template.md`
   - **Tiger** (เสี่ยงจริง คุมไม่ได้โดยตรง) → สร้างระบบเตือนภัยล่วงหน้า
   - **Paper Tiger** (ดูน่ากลัวแต่แก้ได้ด้วยขั้นตอน) → ให้ผู้เชี่ยวชาญชี้แจงวิธีปลดล็อก
   - **Elephant in the Room** (คอขวดภายในที่ไม่มีใครพูด) → นำเข้าที่ประชุมผู้บริหารก่อนเซ็นสัญญา
4. **แปลงเป็นแผนป้องกัน** — นำมาตรการที่ได้ไปบรรจุในแผนหลักผ่าน `project-plan`

## Output

- ตาราง Pre-Mortem Matrix แยก Tiger / Paper Tiger / Elephant in the Room
- ความเสี่ยงแต่ละข้อมี สัญญาณเตือนล่วงหน้า (Early Indicator), มาตรการป้องกัน และผู้รับผิดชอบ
- รายการประเด็นที่ต้องให้ผู้บริหารตัดสินก่อนลงนาม แยกออกมาให้เห็นชัด

## Authority

AI ช่วยได้: ตั้งคำถาม จัดหมวดหมู่ความเสี่ยง เสนอสัญญาณเตือนและมาตรการป้องกัน

ต้องให้มนุษย์ตัดสิน:
- การตัดสินใจเดินหน้า ชะลอ หรือยุติโครงการ
- การลงนามสัญญาและการรับความเสี่ยงแทนองค์กร
- การเปลี่ยนวงเงินหรือขยายเวลาเพื่อลดความเสี่ยง — `budget-allocation`

AI ไม่ประเมินตัวบุคคลว่าเป็นสาเหตุความล้มเหลว การประเมินผลรายบุคคลเป็น `hr-performance-evaluation`

## Handoff

- มาตรการป้องกันที่ตกลงแล้ว ส่งเข้า `project-plan` เพื่อบรรจุในแผนและ Risk Register
- ประเด็น Elephant in the Room ส่งต่อผู้บริหารที่กำกับทีมตาม `manifest/organization.yaml` → `executiveOversight`
- ความเสี่ยงด้านจัดซื้อและงวดเงิน ส่งต่อ AFP

พร้อมส่งต่อเมื่อ: ความเสี่ยงทุกข้อมีเจ้าของมาตรการและสัญญาณเตือนแล้ว

## Guardrails

1. **สมมติว่าล้มเหลวไปแล้ว 100%** — ไม่ถามแบบ "มีอะไรอาจผิดพลาด" เพราะทีมจะตอบแบบระวังตัว
2. **Blameless & Systemic** — ระบุปัญหาที่กระบวนการ ระบบ และข้อจำกัดเชิงโครงสร้าง ไม่โจมตีบุคคล
3. **ทุกความเสี่ยงต้องมีมาตรการจริง** — ถ้าไม่มีสัญญาณเตือนและผู้รับผิดชอบ ถือว่ายังไม่จบ
4. **แยกข้อเท็จจริงจากการคาดการณ์** — สาเหตุที่ระดมได้เป็นสมมติฐาน ไม่ใช่ข้อสรุปว่าจะเกิดจริง
5. **ไม่ใช้ผล Pre-Mortem ตัดสินคน** — ใช้เพื่อปรับแผนและกระบวนการเท่านั้น
